# RFC Process

Запиши процесс RFC команды и один RFC реального изменения и положи их в репозиторий. Слоты промпта — название команды и кейс изменения. Имя файла задаёт кейс. RFC после реализации, предложение без альтернатив и утверждённый RFC, который никуда не ведёт, не подходят.

## Куда писать

`.theory/rfc-process/<кейс>.md`

Один файл на кейс. Имя файла — kebab-case кейса: нижний регистр, слова через дефис, латиница (`Переход с REST на gRPC в модуле уведомлений` → `perehod-s-rest-na-grpc-v-module-uvedomleniy.md`). Команду в имя файла не клади: она остаётся в заголовке. Это не пара сторон и не `index`. Каталог создавай вместе с первым файлом. Повторный запуск для того же кейса обновляет этот файл. Сначала прочитай каталог: если RFC уже лежит под другим написанием того же кейса — обновляй его, второй файл не создавай. Если в файле уже другой кейс — не смешивай: задай один вопрос и остановись. Каталог `.theory/` коммитится вместе с репозиторием.

В этом запуске меняется только файл в `.theory/`. Pull request не открывай, на GitHub ничего не публикуй, исходный код проекта не правь. Шаблон `docs/rfc/0000-template.md` не создавай: запись RFC лежит в этом markdown.

Язык файла — язык документации репозитория. Заголовки блоков оставь как в задании.

## Ход

1. Возьми команду и кейс из сообщения пользователя. Если нет команды или нет кейса — задай один вопрос и остановись до ответа. Если изменение из кейса уже реализовано в коде и документ только описывал бы сделанное — откажись и остановись. Если просят один вариант без сравнения с другими или утвердить RFC, который не станет задачами и не укажет на ADR, — откажись и остановись. Готово, когда названы одна команда и один кейс, а файл — kebab-case кейса.
2. Найди в коде модули, API, хранилища и границы, на которые кейс опирается. Текущее состояние кода — это контекст проблемы, не признак того, что изменение уже выпущено. Если уже есть `.theory/bounded-context-mapping/`, `.theory/context-mapping/`, `.theory/conway-mapping/` или `.theory/runtime-flow-mapping/` — прочитай их и сохрани эти имена, когда они относятся к кейсу. Автора и рецензентов бери из сообщения пользователя или из репозитория (CODEOWNERS, документы). git blame сам по себе не автор RFC: нет имени — `> пробел:`. Готово, когда каждый модуль, владелец, эндпоинт и поток названы именем из репозитория либо помечены `> пробел:`. Модули, владельцев, эндпоинты и потоки не выдумывай.
3. Если файл этого кейса в `.theory/rfc-process/` уже есть — прочитай его и обнови, не создавая второй. Прочитай соседние файлы в том же каталоге. Номер бери следующим свободным: `RFC-0001`, `RFC-0002` и далее. При обновлении оставь прежний номер. «RFC-0001» в задании — образец первого номера, не приказ переписать уже занятый. Критерии и жизненный цикл той же команды в соседних файлах не противоречь: расхождение пометь `> пробел:`. Готово, когда ясно, новый это файл или обновление, и какой у него номер.
4. Закрой блоки задания ниже. Порог, переход статуса, альтернатива, шаг внедрения, риск или открытый вопрос, которых нет ни в коде, ни в сообщении пользователя, пометь `> пробел:` и задай один вопрос. Нужны минимум две альтернативы, которые уже названы. Названных меньше — недостающие пометь `> пробел:`, варианты не выдумывай. Имена из примера (@username, @team-core, «переход с REST на gRPC») не копируй, если это не кейс пользователя. Срок комментариев и итог созвона записывай, только если они есть в сообщении или в репозитории. Готово, когда каждый блок либо заполнен по источнику, либо помечен `> пробел:`.
5. Перед записью проверь антипаттерны. Документ не описывает уже выпущенное изменение. В альтернативах не одна безальтернативная идея. Статус бери из сообщения пользователя. Статус не назван — поставь Draft: запись ещё не проходила review, Approved не ставь. Approved без следующего шага не оставляй: укажи задачу или ADR, куда RFC переходит. Задачи и ADR в репозитории нет — `> пробел:` на ссылку, файл ADR не создавай и статус Approved не ставь. Rejected — с причиной. Superseded — со ссылкой на другой файл в `.theory/rfc-process/`, файла нет — `> пробел:`. Готово, когда текст не расходится с разделом «Не делать».
6. Запиши файл в формате ниже. Готово, когда файл лежит по пути из первого раздела, а ответ пользователю называет этот путь и одну фразу: какая схема зафиксирована до кода и какое решение она готовит для ADR.

## Формат файла

Один markdown-файл. Заголовок `# RFC-NNN: <кейс>`. Под ним команда.

Блок реквизитов списком, не отдельными файлами: автор, статус (Draft, Review, Approved, Rejected или Superseded), дата создания, рецензенты. Нет значения — `> пробел:` у этого пункта. Примеры `@username` и `@team-core` не подставляй.

Разделы второго уровня, в этом порядке:

- «Критерии (Thresholds)» — когда для этой команды RFC обязателен и когда избыточен;
- «Жизненный цикл (Lifecycle)» — этапы Draft → Review → Approved / Rejected / Superseded и правило перехода между ними;
- «Контекст и проблема (Why & What)» — какую проблему решает кейс, почему текущее решение не подходит, каков масштаб;
- «Предлагаемое решение (Proposal)» — техническое описание. Схема, модель данных или API — только именами из репозитория или из сообщения пользователя;
- «Рассмотренные альтернативы (Alternatives)» — какие варианты уже названы, почему отвергнуты, плюсы и минусы;
- «План внедрения и миграции (Rollout & Migration)» — как изменение доходит до продакшена, нужна ли обратная совместимость, как мигрируют данные. Шага нет в источнике — `> пробел:`;
- «Открытые вопросы и риски (Open Questions)» — что ещё не решено. Здесь же компромиссы и риски: чем жертвуем, что с производительностью, безопасностью и поддержкой. В артефакте компромиссы вынесены отдельным блоком «Компромиссы и риски», в задании они входят в этот заголовок — второй заголовок не заводи.

В конце одна строка о результате: при Approved — куда RFC переходит (задача или ADR), при Rejected — причина, при Superseded — ссылка на новый RFC. Отдельный `docs/rfc/0000-template.md` не создавай. Pull request не открывай. Дырка в знаниях — цитата `> пробел:`.

## Задание

Разработай процесс RFC (Request for Comments) для команды <команда>.

План и требования к структуре:

1. Критерии (Thresholds): Четко определи, когда RFC обязателен (например, изменения в API, новые технологии, критичные изменения архитектуры), а когда избыточен.
2. Жизненный цикл (Lifecycle): Опиши этапы (Draft → Review → Approved / Rejected / Superseded) и правила перехода между ними.
3. Шаблон документа: Создай лаконичный Markdown-шаблон, включающий секции:
   - Контекст и проблема (Why & What)
   - Предлагаемое решение (Proposal)
   - Рассмотренные альтернативы (Alternatives)
   - План внедрения и миграции (Rollout & Migration)
   - Открытые вопросы и риски (Open Questions)

В качестве демонстрации заполни этот шаблон, написав RFC-0001 для реального кейса: <кейс>. Пиши на техническом русском языке, избегая лишней канцелярии.

## Шаги

1. Задайте критерии (Threshold). Четко определите, когда RFC обязателен (новый сервис, ломающие изменения API, смена модели данных, влияние на смежные команды).
2. Подготовьте шаблон. Зафиксируйте структуру (Проблема → Решение → Альтернативы → Компромиссы и риски → План внедрения → Открытые вопросы).
3. Назначьте рецензентов (Reviewers). Привлеките владельцев доменов и зависимые команды до написания кода.
4. Запустите сбор обратной связи. Установите сроки для асинхронных комментариев и проведите созвон при необходимости. Все итоги дискуссии зафиксируйте в самом RFC.
5. Зафиксируйте результат. Примите решение. Если утверждено — создайте ADR; если отклонено — заархивируйте с указанием причин; если заменено — дайте ссылку на новый RFC.

## Не делать

- RFC после реализации: документ пишется постфактум. Это превращает процесс в формальный театр, а не инструмент проектирования.
- RFC без альтернатив: предложение без сравнения хотя бы с двумя другими вариантами. Без этого документ становится не обоснованным выбором, а просто навязыванием одной идеи.
- Кладбище RFC: утверждённые документы, которые так и не превратились в задачи или ADR. Знания и договорённости теряются на этапе передачи в разработку.
