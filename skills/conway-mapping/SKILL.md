# Conway Mapping

Спроектируй Conway Map одной системы и запиши её в репозиторий. Слот промпта — название системы или платформы. Карта «так сложилось» без целевого состояния, границы только по репозиториям или должностям и план, где все команды продуктовые, не подходят.

## Куда писать

`.theory/conway-mapping/index.md`

Слот — система или платформа целиком, отдельной сущности нет, поэтому имя файла всегда `index.md`. Название системы — в заголовке. Каталог создавай вместе с первым файлом. Повторный запуск для той же системы обновляет этот файл, второй не создаёт. Если в файле уже записана другая система — не смешивай: задай один вопрос и остановись. Каталог `.theory/` коммитится вместе с репозиторием.

Язык файла — язык документации репозитория. Заголовки блоков оставь как в задании.

## Ход

1. Возьми название системы или платформы из сообщения пользователя. Если его нет — задай один вопрос и остановись до ответа. Если просят только оправдать текущие границы законом Конвея, провести границы по репозиториям или должностям без бизнес-контекстов или сделать все команды продуктовыми — откажись и остановись. Готово, когда названа одна система и файл — `index.md`.
2. Найди в коде модули, сервисы, единицы развёртывания и ограниченные контексты. Контексты бери из кода и из `.theory/bounded-context-mapping/` или `.theory/context-mapping/`, если такой каталог есть. Команду бери из репозитория (CODEOWNERS, документы, каталог команд). Автор коммита и строка git blame сами по себе не имя команды: нет имени команды в репозитории — `> пробел:`. Готово, когда каждая команда, контекст и сервис названы именем из репозитория либо помечены `> пробел:`. Модули, сервисы, команды и контракты не выдумывай.
3. Если `index.md` уже есть — прочитай его и обнови. Прочитай соседние файлы в `.theory/conway-mapping/` и сохрани уже принятые имена команд и границ. Готово, когда ясно, что обновляется один файл той же системы.
4. Закрой блоки задания ниже. Несовпадение, которого не подтверждают код и документы, пометь `> пробел:` и задай один вопрос. Целевые шаги пиши только для подтверждённых зон. Нужны 2–3 зоны: подтверждённых меньше — оставшиеся пункты пометь `> пробел:`, зоны не выдумывай. Платформенную или поддерживающую команду не стирай и не назначай, если её нет в репозитории: пометь `> пробел:`. Готово, когда каждый блок либо заполнен по источнику, либо помечен `> пробел:`.
5. Перед записью проверь антипаттерны. У карты есть целевое состояние, не только снимок «так сложилось». Платформенные и поддерживающие команды, которые есть в репозитории, на карте есть. Граница опирается на ограниченный контекст из репозитория или из уже лежащей карты контекстов. Если контекста нет ни у одной строки — файл не пиши: задай один вопрос и остановись. Готово, когда текст не расходится с разделом «Не делать».
6. Запиши файл в формате ниже. Готово, когда файл лежит по пути из первого раздела, а ответ пользователю называет этот путь и одну фразу: где граница модуля и граница команды совпадают и какая скрытая зависимость всё ещё требует согласований.

## Формат файла

Один markdown-файл:

- заголовок `#` с названием системы;
- «Картирование» — markdown-таблица. Колонки: команда, ограниченный контекст (DDD), сервисы или репозитории, тип владения. Одна строка — одна связка цепочки «команда ↔ архитектура ↔ бизнес-контекст». Строка, где одним сервисом владеют несколько команд, остаётся в таблице и помечается как точка трения;
- «Анализ несоответствий» — три списка: «Разделяемые компоненты», «Размытая ответственность», «Проблемы коммуникации». В каждом пункте имена из таблицы;
- «Целевое выравнивание» — по подтверждённой проблемной зоне два пункта: как перерезать лишнюю зависимость в коде или в составе команд и как изменится граница ограниченного контекста или зона ответственности команды.

Отдельные `team_context_service.md` и `registry.md` не создавай. Дырка в знаниях — цитата `> пробел:`.

## Задание

Проанализируй <система> и спроектируй Conway Map, сопоставив структуру организации с технической архитектурой.

1. Картирование (Сопоставь цепочку):
   Организационная структура (Команды / Трайбы) ↔ Техническая архитектура (Микросервисы / Модули) ↔ Бизнес-контекст (Bounded Contexts по DDD).

2. Анализ несоответствий (Выяви Mismatch):
   Найди и подсвети критические расхождения (точки трения):
   - Разделяемые компоненты (Один сервис/модуль разрабатывают несколько команд).
   - Размытая ответственность (Одна команда отвечает за несколько несвязанных доменов).
   - Проблемы коммуникации (Высокая связанность между командами из-за архитектурных зависимостей).

3. Целевое выравнивание (Target State):
   Предложи конкретные шаги по устранению 2–3 ключевых проблемных зон. Для каждой зоны опиши:
   - Как перерезать лишние зависимости (в коде или в структуре команд).
   - Как изменится граница Bounded Context или зона ответственности команды.

Выведи результат в виде структурированных списков или Markdown-таблицы для наглядности.

## Шаги

1. Инвентаризация команд. Определите, кто и чем владеет — по штатному расписанию и по факту (через git blame, дежурства и логи коммитов).
2. Инвентаризация границ системы. Выделите модули, микросервисы, изолированные контексты (Bounded Contexts) и независимые единицы развертывания.
3. Наложение карт. Сопоставьте структуры. Идеальный фокус: одна команда — один контекст, один сервис — одна команда.
4. Поиск точек трения. Найдите места, где для одного релиза или изменения требуется синхронизация трех и более команд.
5. Планирование выравнивания. Спроектируйте целевое состояние (разделение команды, распил сервиса или выделение платформенной команды) с учетом компромиссов.

## Не делать

- Закон Конвея как оправдание плохой архитектуры: «Так сложилось» — не стратегия; карта показывает куда двигаться.
- Игнорирование платформенных команд: попытка сделать абсолютно все команды продуктовыми. Без выделения платформенных и поддерживающих команд (инфраструктура, общие инструменты) продуктовые команды быстро увязнут в рутине.
- Conway Mapping без Context Mapping: проводить границы только по репозиториям или должностям, забывая про логику бизнеса. Без карты ограниченных контекстов (DDD) вы получите ложную картину и не увидите реальных конфликтов в коде.
