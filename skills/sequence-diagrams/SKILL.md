# Sequence Diagrams

Запиши диаграмму последовательности одного сценария и положи её в репозиторий. Слот промпта — название сценария. Скобку формата в промпте у пользователя не спрашивай: диаграмма пишется в тот же файл. Вся система, схема на десятки участников и перечень каждого SQL-запроса не подходят.

## Куда писать

`.theory/sequence-diagrams/<сценарий>.md`

Один файл на сценарий. Имя файла — kebab-case сценария: нижний регистр, слова через дефис, латиница (`Оплата заказа` → `oplata-zakaza.md`, `OrderService` в имени сценария → `order-service.md`). Слот — один сценарий, не система, поэтому файл не `index.md`. Каталог создавай вместе с первым файлом. Повторный запуск для того же сценария обновляет этот файл. Сначала прочитай каталог: если диаграмма уже лежит под другим написанием того же имени — обновляй её, второй файл не создавай. Если в файле уже другой сценарий — не смешивай: задай один вопрос и остановись. Каталог `.theory/` коммитится вместе с репозиторием.

Язык файла — язык документации репозитория. Заголовки блоков оставь как в задании.

## Ход

1. Возьми сценарий из сообщения пользователя. Если его нет — задай один вопрос и остановись до ответа. Если названа система целиком, несколько сценариев или диаграмма на десятки участников — задай один вопрос, какой один сценарий писать, и остановись. Несколько файлов за один запуск не создавай. Если просят расписать каждый SQL-запрос или выстроить шаги без строгого порядка сверху вниз — откажись и остановись. Готово, когда назван один сценарий и файл — его kebab-case.
2. Найди этот сценарий в коде: участников, вызовы, топики, очереди, события и ответы. Не проектируй обмен заново. Если в `.theory/runtime-flow-mapping/` уже есть этот сценарий — возьми оттуда список переходов и только детализируй его. Если уже есть `.theory/dependency-mapping/`, `.theory/c4-model/` или `.theory/modular-monolith/` — прочитай их и сохрани эти имена, когда они относятся к сценарию. Готово, когда каждый участник, топик, эндпоинт и событие названы именем из репозитория либо помечены `> пробел:`. Модули, брокеры и сообщения не выдумывай.
3. Если файл этого сценария в `.theory/sequence-diagrams/` уже есть — прочитай его и обнови, не создавая второй. Прочитай соседние файлы в том же каталоге и сохрани уже принятые имена. Готово, когда ясно, какой файл обновлять.
4. Закрой блоки задания ниже. Участник, стрелка, топик, поле события или ветка `alt`/`opt`, которых нет в коде и в карте потока, пометь `> пробел:` и задай один вопрос. Асинхронного шага в коде нет — стрелку `->>` не рисуй и брокер не подставляй: пометь `> пробел:`. Имена из примера (Клиент, API Gateway, orders.v1, OrderCreated, Сервис обработки) не копируй. Распределённого трейса в репозитории нет — сверку с трейсом пометь `> пробел:`. Готово, когда каждый блок либо заполнен по источнику, либо помечен `> пробел:`.
5. Перед записью проверь антипаттерны. На схеме один сценарий и участники одного ограниченного контекста. Вызовы к хранилищу сгруппированы («Сохранить заказ»), а не список INSERT и UPDATE. Порядок сообщений сверху вниз — это порядок выполнения. Готово, когда текст не расходится с разделом «Не делать».
6. Запиши файл в формате ниже. Готово, когда файл лежит по пути из первого раздела, а ответ пользователю называет этот путь и одну фразу: в каком порядке зафиксированы сообщения и что расхождение с распределённым трейсом означает устаревшее архитектурное знание.

## Формат файла

Один markdown-файл. Заголовок `#` — название сценария.

Разделы второго уровня, в этом порядке:

- «Участники» — линии жизни с типом: сервисы (инициатор, продюсер, консьюмер), инфраструктура (брокер, очередь или топик, база), внешние системы (API). Имена из репозитория;
- «Логика взаимодействия» — основной успешный путь по времени. Синхронный вызов — `->`, ответ — `-->`, асинхронная публикация и доставка — `->>`. У асинхронного шага название топика или очереди и структура ключевого события. Период, когда участник занят обработкой, — activate и deactivate;
- «Граничные случаи» — ошибки валидации, таймауты и retry, которые есть в коде, блоками `alt` или `opt`.

В конце один fenced-блок диаграммы в этом же файле: `mermaid` с `sequenceDiagram`, autonumber и title сценария. Те же участники и тот же порядок стрелок, что в разделах выше. Репозиторий уже ведёт последовательности на PlantUML — тогда один блок PlantUML, mermaid рядом не добавляй. Под блоком одна строка сверки с распределённым трейсом; трейса нет — `> пробел:`. Отдельный `standard-diagram.md` не создавай. Дырка в знаниях — цитата `> пробел:`.

## Задание

Спроектируй Sequence Diagram для асинхронного сценария: <сценарий>.

1. Участники (Укажи типы):
   - Сервисы (Инициаторы, Продюсеры, Консьюмеры)
   - Инфраструктура (Брокеры сообщений, Очереди/Топики, БД)
   - Внешние системы (API)
2. Логика взаимодействия:
   - Синхронные вызовы (HTTP/gRPC) обозначай прямыми стрелками `->`, ответы — пунктиром `-->`.
   - Асинхронную публикацию событий в брокер и их доставку консьюмерам обозначай стрелками `->>`.
   - Явно укажи названия топиков/очередей и структуру ключевых событий.
3. Граничные случаи:
   - Изолируй альтернативные сценарии (ошибки валидации, таймауты, retry-логику) в блоки `alt` или `opt`.

Сгенерируй код диаграммы в формате PlantUML или Mermaid.

## Шаги

1. Возьмите один сценарий из Runtime Flow Mapping. Не проектируйте с нуля — детализируйте конкретный цепочечный список переходов (hop list).
2. Определите линии жизни (lifelines). Вынесите каждого участника в отдельную колонку (сервис, база данных, брокер, внешнее API).
3. Отрисуйте основной успешный сценарий (happy path). Синхронные вызовы обозначайте сплошными стрелками, асинхронные сообщения — открытыми (пунктирными или стрелками без заливки).
4. Добавьте блоки активности. Выделите периоды времени, когда компонент сфокусирован на обработке конкретного вызова.
5. Проверьте схему по реальному трейсу. Сверьте получившуюся диаграмму с распределенным трейсом (distributed trace) в тестовой среде (staging).

## Не делать

- Диаграмма на 30 участников: перегружает схему. Разбивайте процесс на отдельные поддиаграммы (sub-diagrams) в рамках своих ограниченных контекстов (bounded contexts).
- Детализация до каждого SQL-запроса: превращает схему в нечитаемый лог. Группируйте вызовы: пишите «Сохранить заказ» вместо перечисления 15 мелких INSERT/UPDATE.
- Игнорирование оси времени: проектирование шагов без жесткой хронологии. Диаграмма последовательности теряет смысл, если нарушен строгий порядок выполнения сверху вниз.
