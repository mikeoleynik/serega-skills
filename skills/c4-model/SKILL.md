# C4 Model

Собери модель C4 одной системы и запиши её в репозиторий. Слоты промпта — название системы, стек и основные акторы. Все четыре уровня сразу на всю систему, Level 4 на каждый компонент и смесь уровней на одной диаграмме не подходят.

## Куда писать

`.theory/c4-model/index.md`

Слот системы — проект целиком, отдельной сущности нет, поэтому имя файла всегда `index.md`. Название системы — в заголовке. Стек и акторы в имя файла не входят. Каталог создавай вместе с первым файлом. Повторный запуск для той же системы обновляет этот файл, второй не создаёт. Если в файле уже записана другая система — не смешивай: задай один вопрос и остановись. Каталог `.theory/` коммитится вместе с репозиторием.

Язык файла — язык документации репозитория. Заголовки блоков оставь как в задании.

## Ход

1. Возьми название системы из сообщения пользователя. Если его нет — задай один вопрос и остановись до ответа. Стек и акторов, если их не назвали, в этом шаге не спрашивай: их закроет шаг 2. Если просят все четыре уровня сразу на всю систему, Level 4 для каждого компонента или одну диаграмму со смешанными уровнями — откажись и остановись. Готово, когда система названа и файл — `index.md`.
2. Найди в коде контейнеры, компоненты, акторов, внешние системы и стек. Для диаграммы компонентов возьми контейнер, который пользователь назвал. Если не назвал и в коде один основной контейнер — бери его. Если ключевых несколько и неясно, какой раскрывать, пометь `> пробел:` и задай один вопрос, не выбирай за пользователя. Готово, когда каждое имя на диаграммах взято из репозитория либо помечено `> пробел:`. Модули, сервисы и тесты не выдумывай.
3. Если `index.md` уже есть — прочитай его и обнови. Прочитай соседние файлы в `.theory/c4-model/` и сохрани уже принятые имена. Готово, когда ясно, что обновляется один файл той же системы.
4. Закрой блоки задания ниже. Уровень 4 рисуй только для критической части, которую видно в коде или которую назвал пользователь. Нет такой части — в разделе напиши, что уровень не нужен, и классы не выдумывай. Стек, актор, контейнер или решение, которых нет в коде, пометь `> пробел:` и задай один вопрос. Шаг «Держите диаграммы живыми» не превращай в новый пайплайн: способ обновления возьми из репозитория, иначе `> пробел:`. Готово, когда каждый блок либо заполнен по источнику, либо помечен `> пробел:`.
5. Перед записью проверь антипаттерны. Контекст и контейнеры покрывают систему. Компоненты — один контейнер. Код — только критическое место, либо явная пометка, что уровень не нужен. На одной диаграмме один уровень абстракции. Не пиши, что команда диаграмму уже приняла, если в репозитории этого нет. Готово, когда текст не расходится с разделом «Не делать».
6. Запиши файл в формате ниже. Готово, когда файл лежит по пути из первого раздела, а ответ пользователю называет этот путь и одну фразу: какие уровни абстракции зафиксированы отдельными диаграммами и какой контейнер раскрыт на уровне компонентов.

## Формат файла

Один markdown-файл:

- заголовок `#` с названием системы;
- блок «Мой контекст»: система, стек, основные акторы;
- четыре раздела второго уровня, в этом порядке: «Контекстная диаграмма», «Диаграмма контейнеров», «Диаграмма компонентов», «Кодовая диаграмма»;
- в каждом разделе краткое текстовое описание, ключевые архитектурные решения и один fenced-блок;
- диалект один на весь файл: `dsl` (Structurizr, `workspace { ... }`) или `plantuml`. Бери тот, что уже есть в репозитории. Если нет ни того ни другого — Structurizr DSL;
- «Диаграмма компонентов» детализирует один контейнер, и его имя есть в заголовке раздела;
- «Кодовая диаграмма» — только критическая часть. Если она не нужна, в разделе одна фраза об этом, без пустой диаграммы;
- в конце файла одна фраза, как диаграммы остаются живыми. Пайплайн CI не добавляй.

Отдельные `.dsl` и `.puml` не создавай. Дырка в знаниях — цитата `> пробел:`.

## Задание

Ты — архитектор программного обеспечения.
Проанализируй мою кодовую базу и создай модель C4 со следующими уровнями:

1. Контекстная диаграмма — покажи систему в окружении внешних актёров и систем.
2. Диаграмма контейнеров — разбей систему на отдельно развёртываемые единицы.
3. Диаграмма компонентов — детализируй один из ключевых контейнеров.
4. Кодовая диаграмма — при необходимости покажи детали реализации.

Мой контекст:
- Система: <система>
- Стек: <стек>
- Основные акторы: <акторы>

Для каждого уровня:
- Выведи DSL Structurizr (workspace {...}) или PlantUML-диаграмму
- Добавь краткое текстовое описание
- Отметь ключевые архитектурные решения

## Шаги

1. Контекст (Level 1). Нарисуйте систему как один блок. Определите пользователей и внешние системы, с которыми она взаимодействует.
2. Контейнеры (Level 2). Разбейте систему на запускаемые единицы (веб-приложения, API, базы данных). Покажите, как они общаются.
3. Компоненты (Level 3). Внутри ключевого контейнера покажите основные компоненты и их ответственность.
4. Код (Level 4). Для критических компонентов покажите ключевые классы/модули (опционально).
5. Держите диаграммы живыми. Интегрируйте генерацию диаграмм в CI/CD (Structurizr DSL + Structurizr Lite) или обновляйте вручную при каждом значимом архитектурном решении.

## Не делать

- Рисовать все 4 уровня сразу для всей системы: начните с контекста, углубляйтесь только в проблемные зоны.
- Детализировать Level 4 для каждого компонента: Level 4 опционален — только для критических частей системы.
- Делать диаграммы в одиночку: C4 — инструмент коллективного понимания. Диаграмма, нарисованная в одностороннем порядке и спущенная команде, не строит теорию — она создаёт ещё один артефакт, который никто не читает.
- Смешивать уровни абстракции: таблица БД и микросервис — разные уровни C4. Смешение уровней уничтожает главную ценность модели — предсказуемую степень детализации.
