# System Quality Attributes

Собери карту quality attributes одной системы и запиши её в репозиторий. Слот промпта — название системы или её контекст. Список, где все -ilities одинаково важны, и каталог без измеримого сигнала не подходят.

## Куда писать

`.theory/system-quality-attributes/index.md`

Слот — система целиком, отдельной сущности нет, поэтому имя файла всегда `index.md`. Название системы — в заголовке. Плейсхолдер «название / контекст» — это та же система: контекст не получает свой файл. Назван только контекст, а системы нет — имя контекста встаёт в заголовок того же `index.md`. Каталог создавай вместе с первым файлом. Повторный запуск для той же системы обновляет этот файл. Контекст той же системы дополняет его, второй файл не создаёт. Если в файле уже другая система — не смешивай: задай один вопрос и остановись. Каталог `.theory/` коммитится вместе с репозиторием.

Язык файла — язык документации репозитория. Заголовки блоков оставь как в задании.

## Ход

1. Возьми название системы из сообщения пользователя. Назван только контекст — его имени хватает для заголовка того же `index.md`. Если нет ни системы, ни контекста — задай один вопрос и остановись до ответа. Если просят пометить все -ilities высоким приоритетом или выдать каталог слов без метрик — откажись и остановись. Готово, когда система или её контекст названы и файл — `index.md`.
2. Найди в коде, SLO, дашбордах, CI и документах атрибуты, которые система уже измеряет или называет. Ожидания бизнеса, эксплуатации, разработки и безопасности бери оттуда же. Атрибут выбирай из групп каталога: операционные (availability, reliability, fault-tolerance, recoverability, resilience, scalability, elasticity), развитие (modifiability, maintainability, extensibility, evolvability, testability, deployability), пользовательские (usability, learnability, accessibility, performance), интеграция (interoperability, portability, compatibility), доверие (security, safety, auditability). Если уже есть `.theory/c4-model/`, `.theory/system-context-mapping/`, `.theory/architecture-decision-mapping/` или `.theory/evolutionary-architecture/` — прочитай их и сохрани эти имена системы, границ и характеристик, где атрибут тот же. Готово, когда каждый атрибут, сигнал и стейкхолдер взяты из репозитория либо помечены `> пробел:`. Метрики, SLO и ожидания не выдумывай.
3. Если `index.md` уже есть — прочитай его и обнови. В файле уже другая система — не смешивай: задай один вопрос и остановись. Прочитай соседние файлы в `.theory/system-quality-attributes/` и сохрани уже принятые имена атрибутов. Готово, когда ясно, что обновляется один файл той же системы.
4. Закрой блоки задания ниже. Диапазон 8–12 — потолок задания, не квота: пиши атрибуты, которые подтверждены репозиторием или сообщением пользователя. Недостающие до восьми не добирай примерами из задания (99.9% uptime, RTO, lead time, error budget, CVE). Топ-5 — только среди подтверждённых. Конфликт, анти-цель или доминирующий набор, которых нет в источниках, пометь `> пробел:` и задай один вопрос. Весь справочник -ilities в файл не копируй. Готово, когда каждый блок либо заполнен по источнику, либо помечен `> пробел:`.
5. Перед записью проверь антипаттерны. Есть явные анти-цели: не все строки с высшим приоритетом. У одного атрибута одно имя, «performance», «scalability» и «responsiveness» не схлопнуты в одно слово. У каждого выбранного атрибута измеримый сигнал. Сигнала нет — в ячейке `> пробел:`, строку выдуманной метрикой не закрывай. Готово, когда текст не расходится с разделом «Не делать».
6. Запиши файл в формате ниже. ADR, выбор стиля и фитнес-функции этим запуском не создавай: пары ниже остаются готовыми для них. Если такие файлы уже лежат в `.theory/`, сохрани их имена. Готово, когда файл лежит по пути из первого раздела, а ответ пользователю называет этот путь и одну фразу: какой баланс атрибутов зафиксирован и какая пара конфликтует, так что одно и то же слово больше не значит разное.

## Формат файла

Один markdown-файл:

- заголовок `#` с названием системы;
- «Стейкхолдеры и их ожидания» — бизнес, эксплуатация, разработка, безопасность и что каждый ждёт от системы;
- «Атрибуты» — выбранные 8–12, у каждого краткое определение в контексте продукта и измеримый сигнал (метрика, сценарий или SLO);
- «Приоритеты и конфликтующие пары» — markdown-таблица топ-5. Колонки: приоритет (MoSCoW или вес 1–5), quality attribute, сигнал / метрика, конфликтует с. Под таблицей те же конфликты списком из 3–5 пар;
- «Наборы» — какой из FURPS, RASUI, RAMS и agility subset доминирует по этому топу;
- «Анти-цели» — какие -ilities сознательно жертвуют на текущем этапе и почему.

Отдельные `quality-priorities.md` и `ilities-catalog.md` не создавай. Дырка в знаниях — цитата `> пробел:`.

## Задание

Построй карту quality attributes для системы: <система>.

1. Собери стейкхолдеров и их ожидания: бизнес, эксплуатация, разработка, безопасность.
2. Из каталога -ilities выбери 8–12 релевантных атрибутов (не «все подряд»). Для каждого — краткое определение в контексте продукта и измеримый сигнал (метрика, сценарий, SLO).
3. Ранжируй топ-5 по важности (MoSCoW или веса 1–5). Явно укажи конфликтующие пары (например, availability ↔ cost, modifiability ↔ performance).
4. Сопоставь приоритеты с известными наборами (FURPS, RASUI, RAMS, agility subset) — что у вас доминирует.
5. Зафиксируй «анти-цели»: какие -ilities сознательно жертвуем на текущем этапе и почему.

Результат: таблица приоритетов + 3–5 trade-off, готовых для ADR и выбора архитектурного стиля.

## Шаги

1. Соберите ожидания стейкхолдеров. Бизнес, ops, dev, security — у каждого свой набор -ilities.
2. Отфильтруйте каталог. 8–12 атрибутов, релевантных продукту; не копируйте весь Wikipedia-список.
3. Определите измеримость. Для каждого атрибута — метрика, сценарий или SLO, иначе приоритеты не проверить.
4. Ранжируйте и найдите конфликты. Топ-5 важных; пары взаимоисключающих целей (availability vs cost).
5. Свяжите с решениями. Используйте приоритеты в ADR, выборе стиля (FASA) и fitness functions (Evolutionary Architecture).

## Не делать

- Все -ilities «высокий приоритет»: без жертв архитектура не выбирается. Анти-цели фиксируй явно.
- Разные термины в одной команде: «performance», «scalability» и «responsiveness» — разные слова. Глоссарий в файле один.
- Каталог без метрик: список слов не меняет поведение. На атрибут нужен измеримый сигнал.
