# Event-Driven Architecture

Спроектируй событийную интеграцию одного сценария или одного ограниченного контекста и запиши её в репозиторий. Слот промпта — сценарий или ограниченный контекст и текущая проблема. События в роли команд, общая база у подписчиков и запуск без сквозных идентификаторов не подходят.

## Куда писать

`.theory/event-driven-architecture/<сценарий>.md`

Один файл на сценарий. Имя файла — kebab-case сценария: нижний регистр, слова через дефис, латиница (`Оформление заказа` → `oformlenie-zakaza.md`). Отдельного сценария нет, назван только ограниченный контекст — kebab-case этого контекста. Проблему в имя файла не клади: она остаётся в заголовке. Это не `index`: слот — один сценарий или один контекст, не вся система. Каталог создавай вместе с первым файлом. Повторный запуск для того же сценария или того же контекста обновляет этот файл. Сначала прочитай каталог: если интеграция уже лежит под другим написанием того же имени — обновляй её, второй файл не создавай. Если в файле уже другой сценарий или другой контекст — не смешивай: задай один вопрос и остановись. Каталог `.theory/` коммитится вместе с репозиторием.

Язык файла — язык документации репозитория. Заголовки блоков оставь как в задании.

## Ход

1. Возьми сценарий или ограниченный контекст и текущую проблему из сообщения пользователя. Если нет сценария и нет контекста, или нет проблемы — задай один вопрос и остановись до ответа. Если просят именовать события командами, связать подписчиков общей базой или внутренней логикой друг друга, либо запустить обмен без correlation id и trace id — откажись и остановись. Готово, когда есть один сценарий или один контекст, одна проблема и понятно, какой файл писать.
2. Найди в коде синхронные вызовы (RPC, REST), издателей, подписчиков, брокеры, очереди и уже существующие события на этом пути. Если в `.theory/bounded-context-mapping/` или `.theory/context-mapping/` уже есть контексты или карта — прочитай их и сохрани эти имена. Готово, когда каждый сервис, вызов и событие названы именем из репозитория либо помечены `> пробел:`. Модули, сервисы, события и команды не выдумывай. Имя события, которого ещё нет в коде, допустимо только как факт в прошедшем времени по существующему вызову; вызов не найден — `> пробел:`.
3. Если файл этого сценария или контекста в `.theory/event-driven-architecture/` уже есть — прочитай его и обнови, не создавая второй. Прочитай соседние файлы в том же каталоге и сохрани уже принятые имена событий и сервисов. Готово, когда ясно, какой файл обновлять.
4. Закрой блоки задания ниже. Нужны 2–3 синхронных вызова, которые есть в коде на пути этой проблемы. В коде их меньше — запиши найденные, остальные пункты пометь `> пробел:`, вызовы не выдумывай. Издатель, подписчик, брокер, схема, DLQ, retry и пилот, которых нет в коде, пометь `> пробел:`. Имена из примера (OrderPlaced, Kafka, Rabbit) не копируй. Готово, когда каждый блок либо заполнен по источнику, либо помечен `> пробел:`.
5. Перед записью проверь антипаттерны. Имя события — существительное и глагол в прошедшем времени, свершившийся факт. Подписчик не зависит от внутренностей издателя и не делит с ним базу. В гарантиях есть correlation id и trace id: имя заголовка бери из репозитория, нет имени — `> пробел:`, раздел не пропускай. Пилот — одно событие с наименьшим числом подписчиков среди тех, что уже есть в спецификации; все пути критические и зона поражения не видна — пилот пометь `> пробел:`, не объявляй безопасным критический процесс. Готово, когда текст не расходится с разделом «Не делать».
6. Запиши файл в формате ниже. Готово, когда файл лежит по пути из первого раздела, а ответ пользователю называет этот путь и одну фразу: издатель не знает реализации подписчиков и связан с ними контрактом события, поэтому сбой одного сервиса не тянет остальные.

## Формат файла

Один markdown-файл:

- заголовок `#` со сценарием или ограниченным контекстом и одной строкой текущей проблемы;
- пять разделов второго уровня, в этом порядке: «Анализ потока данных», «Спецификация событий (Domain Events)», «Инженерные гарантии», «Компромиссы (Trade-offs)», «Пилотный запуск»;
- в «Анализе потока данных» — 2–3 существующих синхронных вызова и чем каждый заменяется в асинхронном потоке. Здесь же один блок `mermaid` с `sequenceDiagram`: участники и сообщения — имена из репозитория. Брокер, которого нет в коде, — `> пробел:`;
- в «Спецификации событий» — markdown-таблица. Колонки: событие, версия схемы, издатель, подписчики, бизнес-факт. Под таблицей по одному fenced-блоку `json` на событие: метаданные (идентификатор схемы, идентификатор события, тип, версия, время, издатель, correlation id, trace id) и полезная нагрузка. Поля, которых нет в коде, — `> пробел:` внутри блока, значения не выдумывай;
- в «Инженерных гарантиях» — идемпотентность на стороне подписчика, DLQ и retry. Имя очереди, ключа или политики бери из кода; механизма нет — опиши, какой нужен, и пометь имя `> пробел:`;
- в «Компромиссах» — где появляется согласованность в конечном счёте и как это видно пользователю. Способ смягчения, которого нет в продукте, — `> пробел:`;
- в «Пилотном запуске» — одно стартовое событие из спецификации и почему зона поражения меньше, чем у остальных.

Отдельные `sequence-diagram.md`, `registry-table.md` и `event-schema.json` не создавай. Дырка в знаниях — цитата `> пробел:`.

## Задание

Спроектируй интеграцию на базе Event-Driven Architecture (EDA) для следующего контекста: <сценарий или ограниченный контекст и текущая проблема>.

Выполни проектирование по следующим шагам и оформи ответ строго по структуре:

1. Анализ потока данных: Выдели 2–3 существующих синхронных вызова (RPC/REST) и покажи, как они заменяются на асинхронный Event Flow.
2. Спецификация событий (Domain Events): Определи ключевые бизнес-события в формате «Существительное + Глагол в прошедшем времени». Укажи для каждого: Publisher, Subscribers и пример Event Schema (JSON) с метаданными и полезной нагрузкой (Payload).
3. Инженерные гарантии: Предложи конкретную стратегию обеспечения идемпотентности на стороне подписчиков и схему обработки ошибок (DLQ, Retry Policy).
4. Компромиссы (Trade-offs): Опиши возникающие риски согласованности в конечном счете (Eventual Consistency) и способы их минимизации для пользователя.
5. Пилотный запуск: Предложи одно стартовое событие для MVP с минимальной зоной поражения (Blast Radius), которое позволит протестировать инфраструктуру без риска для критических процессов.

## Шаги

1. Найдите точки жесткой синхронной связи. Выявите цепочки вызовов, где сбой в одном сервисе каскадно ломает остальные.
2. Выделите доменные события. Сформулируйте свершившиеся факты в прошедшем времени, например: OrderPlaced (Заказ Оформлен), PaymentCaptured (Оплата Поступила).
3. Спроектируйте контракты. Зафиксируйте схемы данных, правила версионирования и обеспечения обратной совместимости.
4. Настройте семантику доставки. Заложите гарантированную доставку как минимум один раз (at-least-once), обеспечьте идемпотентность обработчиков и настройте очередь невалидных сообщений (DLQ).
5. Запустите пилотный поток. Начните с одного события, одного издателя и 1–2 подписчиков, чтобы протестировать и валидировать работу инфраструктуры в продакшене.

## Не делать

- События в роли команд: именование CreateOrder — это команда, приказ выполнить действие. Событие — свершившийся факт в прошедшем времени: OrderCreated.
- Распределенный монолит через события: обработчики, завязанные на внутреннюю логику друг друга или на общую базу, — не слабая связанность.
- Событийная архитектура без сквозного мониторинга: без correlation id и trace id через брокер обмен нечем отлаживать.
