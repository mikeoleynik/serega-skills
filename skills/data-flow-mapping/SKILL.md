# Data Flow Mapping

Построй карту движения данных одной сущности и запиши её в репозиторий. Слот промпта — имя сущности. Вся система целиком не подходит.

## Куда писать

`.theory/data-flow-mapping/<сущность>.md`

Имя файла — kebab-case сущности (`Order` → `order.md`). Каталог создавай вместе с первым файлом. Повторный запуск для той же сущности обновляет этот файл. Каталог `.theory/` коммитится вместе с репозиторием.

Язык файла — язык документации репозитория. Заголовки блоков оставь как в задании.

## Ход

1. Возьми сущность из сообщения пользователя. Если её нет — задай один вопрос и остановись до ответа. Готово, когда есть одно имя сущности, а не система целиком.
2. Найди эту сущность в коде: типы, таблицы, события, очереди, кэши. Готово, когда каждый узел карты назван именем из репозитория либо помечен `> пробел:`.
3. Если `.theory/data-flow-mapping/<сущность>.md` уже есть — прочитай его и обнови, не создавая второй файл. Прочитай соседние карты в том же каталоге и сохрани уже принятые имена.
4. Закрой блоки задания ниже. Шаг, который код не подтверждает, пометь `> пробел:` и задай один вопрос. Не заполняй его догадкой.
5. Перед записью проверь антипаттерны. Убери из карты вызовы сервисов, которые не двигают данные, и не склеивай несколько сущностей в один граф.
6. Запиши файл в формате ниже. Готово, когда файл лежит по пути из первого раздела, а ответ пользователю называет этот путь и одну фразу: где первоисточник, где копии и где данные могут задержаться или разойтись.

## Формат файла

Один markdown-файл:

- заголовок `#` с именем сущности;
- четыре раздела второго уровня, в этом порядке: «Маршрут данных», «Синхронизация и события», «Уязвимые зоны», «Безопасность»;
- в конце один блок `mermaid` с `flowchart LR`. Узлы с побочными эффектами подсвети.

Дырка в знаниях — цитата `> пробел:` с тем, чего нет в коде. Не заводи второй файл и не выноси схему в отдельный `.mmd`.

## Задание

Построй Data Flow Map для сущности: <сущность>.

Проанализируй и пошагово опиши полный жизненный цикл данных по следующим блокам:

1. Маршрут данных: Источники (кто/что порождает), узлы трансформации (бизнес-логика), места хранения (БД, кэш) и конечные потребители.
2. Синхронизация и события: Точки изменения состояния, связанные с ними события (Events) и области с отложенной согласованностью (Eventual Consistency).
3. Уязвимые зоны: Укажи узлы, где данные могут застрять (Race Conditions, зависшие очереди) или рассинхронизироваться (дублирование между сервисами).
4. Безопасность: Выдели критичные узлы, где обрабатываются или хранятся персональные данные (PII).

Результат — структурированный текст и схема Mermaid. Акцент на побочных эффектах (side-effects).

## Шаги

1. Выберите одну сущность или поток событий. Начните с конкретного объекта (например, Order, Payment, UserProfile), а не со всей системы сразу.
2. Найдите первоисточник (System of Record). Определите, какая база или сервис хранит каноническую копию этих данных.
3. Проследите все копии. Найдите реплики для чтения, кэши и денормализованные представления в других сервисах.
4. Зафиксируйте трансформации. Опишите каждый шаг изменения формы данных: обогащение, маппинг, агрегацию.
5. Выделите события. Определите, какие доменные события публикуются при изменении состояния сущности.

## Не делать

- Путать поток данных и поток управления: вызовы сервисов — не движение данных между ними.
- Игнорировать асинхронность: задержки репликации и лаги очередей — часть потока данных.
- Делать один граф на всю систему: одна бизнес-сущность или один поток событий.
