# Context Mapping

Построй Context Map одной системы и запиши её в репозиторий. Слот промпта — название системы или краткое описание. Общее ядро на всех связях, ACL как один маппер DTO в контроллере и карта без legacy не подходят.

## Куда писать

`.theory/context-mapping/index.md`

Слот — система целиком, отдельной сущности нет, поэтому имя файла всегда `index.md`. Название системы — в заголовке. Каталог создавай вместе с первым файлом. Повторный запуск для той же системы обновляет этот файл, второй не создаёт. Если в файле уже записана другая система — не смешивай: задай один вопрос и остановись. Каталог `.theory/` коммитится вместе с репозиторием.

Язык файла — язык документации репозитория. Заголовки блоков оставь как в задании.

## Ход

1. Возьми название системы или краткое описание из сообщения пользователя. Если его нет — задай один вопрос и остановись до ответа. Если просят общее ядро на всех связях, свести ACL к одному классу-мапперу в контроллере или нарисовать карту без legacy — откажись и остановись. Готово, когда названа одна система и файл — `index.md`.
2. Найди в коде ограниченные контексты, интеграции, сущности, события, способы связи и legacy-части. Имена контекстов бери из кода, документов и из `.theory/bounded-context-mapping/`, если каталог есть. Команду бери из репозитория (CODEOWNERS, документы), не из оргсхемы наугад. Готово, когда каждый контекст, связь, сущность и команда названы именем из репозитория либо помечены `> пробел:`. Модули, сервисы, команды и контракты не выдумывай.
3. Если `index.md` уже есть — прочитай его и обнови. Прочитай соседние файлы в `.theory/context-mapping/` и сохрани уже принятые имена контекстов и паттерны связей. Готово, когда ясно, что обновляется один файл той же системы.
4. Закрой блоки задания ниже по каждой интеграции, которая есть в коде. Паттерн, ACL, сущность или способ интеграции, которых нет в коде, пометь `> пробел:` и задай один вопрос. Примеры из задания (REST, RPC, общая БД, Shared Kernel) не подставляй: бери то, что видно в репозитории. Shared Kernel ставь только там, где общее ядро уже есть в коде, не как связь по умолчанию. Готово, когда каждый блок либо заполнен по источнику, либо помечен `> пробел:`.
5. Перед записью проверь антипаттерны. Большинство связей — явный контракт или защитный слой, не общее ядро. ACL изолирует доменную модель, а не сводится к одному мапперу DTO. Legacy из репозитория есть на карте как контекст. Готово, когда текст не расходится с разделом «Не делать».
6. Запиши файл в формате ниже. Готово, когда файл лежит по пути из первого раздела, а ответ пользователю называет этот путь и одну фразу: кто диктует формат данных, кто под него адаптируется и где карта не даёт чужой модели протечь в локальную.

## Формат файла

Один markdown-файл:

- заголовок `#` с названием системы;
- по разделу второго уровня на каждую интеграцию между ограниченными контекстами. Внутри раздела четыре блока, в этом порядке: «Направление и Паттерн связи», «Анализ Защиты (ACL)», «Протекание домена и Данные», «Способ интеграции»;
- в «Направлении и Паттерне связи» — кто Upstream (поставщик), кто Downstream (потребитель) и один паттерн: Partnership, Shared Kernel, Customer-Supplier, Conformist или Open Host Service (OHS) / Published Language (PL);
- в «Анализе Защиты (ACL)» — нужен ли Anti-Corruption Layer на стороне Downstream и почему, если нужен;
- в «Протекании домена и Данных» — какие сущности, события или структуры данных передаются и что рискует попасть в модель потребителя;
- в «Способе интеграции» — технический инструмент, который уже есть в коде;
- «Связи между командами» — какая команда отвечает за каждый контекст. Это шаг алгоритма, в промпте отдельного блока нет;
- в конце один блок `mermaid` с `graph LR`: те же контексты и те же связи, с направлением и паттерном. Подписи узлов — имена из репозитория.

Отдельный `context-map.mmd` не создавай. Дырка в знаниях — цитата `> пробел:`.

## Задание

Построй Context Map для системы: <система>.

Для каждой интеграции между ограниченными контекстами (Bounded Contexts) предоставь анализ в следующем формате:

1. Направление и Паттерн связи: Кто Upstream (поставщик), кто Downstream (потребитель). Выбери паттерн: Partnership, Shared Kernel, Customer-Supplier, Conformist, Open Host Service (OHS) / Published Language (PL).
2. Анализ Защиты (ACL): Нужен ли Anti-Corruption Layer на стороне Downstream? Если да, обоснуй почему (например, сильное различие в доменных моделях).
3. Протекание домена и Данные: Какие именно сущности, события или структуры данных передаются между контекстами? Что рискует «протечь» в чистую модель потребителя?
4. Способ интеграции: Кратко предложи технический инструмент (REST API, RPC, MQ/События, общая БД).

Выдавай результат структурировано, без лишней вводной теории о том, что такое DDD.

## Шаги

1. Соберите список контекстов. Используйте перечень ограниченных контекстов (Bounded Contexts), полученный на этапе проектирования предметной области (DDD).
2. Определите направление зависимостей. Выявите, какие контексты зависят от других на уровне доменной логики (кто потребитель, а кто поставщик данных).
3. Назначьте паттерны отношений. Выберите формат взаимодействия для каждой пары. Например: Партнерство (совместная работа), Заказчик-Поставщик (с возможностью влиять на требования) или Конформист (жесткое подчинение чужой модели, например, при интеграции с legacy).
4. Выделите зоны для защитного слоя (ACL). Определите, где внешние данные могут нарушить чистоту локальной доменной модели, и предусмотрите там слой трансляции (переводчик контрактов).
5. Спроектируйте связи между командами. Примените закон Конвея — зафиксируйте, какие команды разработки отвечают за каждый контекст, чтобы выявить организационные барьеры.

## Не делать

- Общее ядро (Shared Kernel) по умолчанию: совместное использование кода или таблиц БД — это крайняя мера, а не стандарт. Большинство связей должны строиться через явные контракты (Заказчик-Поставщик) или защитные слои.
- ACL как маппер в контроллере: защитный слой — это архитектурная концепция домена, а не один класс преобразования DTO. Он должен полностью изолировать локальную бизнес-логику от внешнего влияния.
- Игнорировать legacy как контекст: старая система или монолит с фиксированной моделью данных — это полноценный участник архитектуры. Чаще всего он выступает жестким поставщиком (Upstream), диктующим свои правила (Конформист), и это необходимо фиксировать на карте.
