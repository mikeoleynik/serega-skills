# Strangler Fig Pattern

Запиши план постепенной замены монолита для одной доменной области и положи его в репозиторий. Слоты промпта — доменная область и монолит. Имя файла задаёт область, монолит остаётся в заголовке. Вырезание всех функций за один шаг, вызов нового сервиса прямо из кода монолита и перенос эндпоинтов без плана данных не подходят.

## Куда писать

`.theory/strangler-fig-pattern/<домен>.md`

Один файл на доменную область. Имя файла — kebab-case области: нижний регистр, слова через дефис, латиница (`Заказы` → `zakazy.md`, `OrderDomain` → `order-domain.md`). Монолит в имя файла не клади: он остаётся в заголовке. Это контекст разрезания, не вторая часть имени. Каталог создавай вместе с первым файлом. Повторный запуск для той же области и того же монолита обновляет этот файл. Сначала прочитай каталог: если план уже лежит под другим написанием того же имени — обновляй его, второй файл не создавай. Если в файле уже другая область или другой монолит — не смешивай: задай один вопрос и остановись. Каталог `.theory/` коммитится вместе с репозиторием.

В этом запуске меняется только файл в `.theory/`. Исходный код проекта не правь. Фасад, прокси и шлюз в репозитории не создавай. Pull request не открывай.

Язык файла — язык документации репозитория. Заголовки блоков оставь как в задании.

## Ход

1. Возьми доменную область и монолит из сообщения пользователя. Если нет области или нет монолита — задай один вопрос и остановись до ответа. Если просят вырезать все функции одним шагом, звать новый сервис прямо из кода монолита без слоя маршрутизации или переносить эндпоинты без плана разделения данных — откажись и остановись. Готово, когда названы одна область и один монолит, а файл — kebab-case области.
2. Найди в коде швы, эндпоинты, фоновые задачи, события и хранилища этой области внутри монолита. Если уже есть `.theory/modular-monolith/`, `.theory/dependency-mapping/`, `.theory/c4-model/` или `.theory/runtime-flow-mapping/` — прочитай их и сохрани эти имена модулей и потоков. Готово, когда каждый шов, эндпоинт, топик и хранилище названы именем из репозитория либо помечены `> пробел:`. Модули, швы и маршруты не выдумывай.
3. Если файл этой области в `.theory/strangler-fig-pattern/` уже есть — прочитай его и обнови, не создавая второй. Прочитай соседние файлы в том же каталоге и сохрани уже принятые имена. В файле уже другой монолит — не смешивай: задай один вопрос и остановись. Готово, когда ясно, какой файл обновлять.
4. Закрой блоки задания ниже. Шов, точка перехвата трафика, первый срез, следующий эндпоинт, способ синхронизации данных, критерий готовности, откат или метрика, которых нет в коде и в сообщении пользователя, пометь `> пробел:` и задай один вопрос. Имена из примера (API Gateway, Новый микросервис, Новая БД) не копируй. Dual write не назначай, если его нет в коде и пользователь его не назвал. Готово, когда каждый блок либо заполнен по источнику, либо помечен `> пробел:`.
5. Перед записью проверь антипаттерны. План идёт срезами, не одним большим взрывом. Перехват трафика описан как маршрутизатор, шлюз, прокси, view или event-router. Разделение и синхронизация данных есть отдельным пунктом; способа нет — `> пробел:`, пункт не выкидывай. Готово, когда текст не расходится с разделом «Не делать».
6. Запиши файл в формате ниже. Шаг алгоритма «Настройте маршрутизацию» остаётся текстом этого плана: слой описан, файла фасада в репозитории не появляется. Готово, когда файл лежит по пути из первого раздела, а ответ пользователю называет этот путь и одну фразу: какой первый срез уходит с монолита и почему продакшен на этом шаге остаётся рабочим.

## Формат файла

Один markdown-файл. Заголовок `#` — доменная область. Под ним имя монолита.

Разделы второго уровня, в этом порядке:

- «Подготовка и Инфраструктура» — швы (seams): как область изолируется в коде и в данных монолита до разрезания; маршрутизация (routing layer): где перехватывается трафик. Точка перехвата — та, что есть в репозитории, иначе `> пробел:`;
- «Стратегия миграции» — первый тонкий срез: один сквозной эндпоинт или одно событие из кода; очередность остальных эндпоинтов, фоновых задач и событий; стратегия данных на переходный период. Среза в коде не видно — `> пробел:`;
- «Протокол безопасности» — чек-лист критериев готовности к следующему шагу, риски и откат (rollback, feature flag), мониторинг (SLI/SLA). Метрики, которых нет в репозитории, — `> пробел:` у пункта. Пункты примера про уже развёрнутый сервис, CI и дашборды не копируй как сделанные.

Один fenced-блок `mermaid` с `graph TD` в этом же файле: клиентский трафик, слой маршрутизации, новый срез и то, что остаётся в монолите. Узлы — имена из репозитория. Синхронизацию данных рисуй, только если она названа. Отдельные `arch-template.md` и `checklist.md` не создавай. Фасад в коде не создавай. Pull request не открывай. Дырка в знаниях — цитата `> пробел:`.

## Задание

Спланируй миграцию по паттерну Strangler Fig для выделения доменной области <домен> из монолита <монолит>.

Сформируй пошаговый технический план, разбитый на следующие блоки:

1. Подготовка и Инфраструктура:
   - Точки сопряжения (Seams): как именно изолируется домен на уровне кода и данных в монолите перед разрезанием.
   - Маршрутизация (Routing Layer): где и как перехватывается трафик (API Gateway, балансировщик, DB-view или event-router).
2. Стратегия миграции (Поэтапный перенос):
   - Первый «тонкий срез» (Vertical Slice): минимальный сквозной сценарий для проверки инфраструктуры в проде с минимальным риском.
   - Очередность переноса: приоритет миграции остальных эндпоинтов, фоновых задач и эвентов.
   - Стратегия работы с данными: как обеспечивается синхронизация или двойная запись (Dual Write) в переходный период.
3. Протокол безопасности для каждого этапа:
   - Критерии готовности (Definition of Done) для перехода к следующему шагу.
   - Риски и стратегия отката (Rollback / Feature Flags).
   - Мониторинг: ключевые метрики (SLI/SLA), доказывающие, что новый сервис работает корректно под нагрузкой.

Ответ должен быть лаконичным, в виде конкретных архитектурных решений и чек-листов, без общих вводных фраз.

## Шаги

1. Определите границу (Seam). Найдите точку, где можно перехватить вызовы — на уровне API Gateway, шины сообщений или feature flag.
2. Настройте маршрутизацию (Facade). Создайте слой проксирования, который будет направлять часть трафика в новый сервис, а остальное — в монолит.
3. Выделите первый срез (Vertical Slice). Выберите один эндпоинт или одно событие — минимальный, но сквозной бизнес-сценарий.
4. Итерируйте. Переносите функциональность шаг за шагом: старый код уменьшается, новый сервис разрастается.
5. Выведите legacy из эксплуатации. Когда трафик упадет до нуля, а данные будут полностью мигрированы — удалите старый код.

## Не делать

- «Большой взрыв» (Big Bang): попытка вырезать все функции сразу за один спринт. Полностью перечеркивает саму идею постепенной и безопасной миграции.
- Замена без маршрутизации: вызов нового сервиса напрямую из кода монолита вместо использования прокси/шлюза. Лишает возможности мгновенно откатить трафик назад.
- Игнорирование миграции данных: перенос эндпоинтов без четкого плана разделения и синхронизации баз данных. Гарантированно приводит к эффекту расщепления сознания (Split-Brain).
