# Refactoring Patterns

Запиши план безопасного рефакторинга одного модуля или класса и положи его в репозиторий. Слот промпта — модуль или класс. Рефакторинг без тестов, переписывание всего сразу и правка самого сложного непокрытого участка первой не подходят.

## Куда писать

`.theory/refactoring-patterns/<модуль-или-класс>.md`

Имя файла — kebab-case модуля или класса: нижний регистр, слова через дефис, латиница (`OrderService` → `order-service.md`). Слот — одна единица, не проект целиком, поэтому файл не `index.md`. Каталог создавай вместе с первым файлом. Повторный запуск для той же единицы обновляет этот файл. Сначала прочитай каталог: если план уже лежит под другим написанием того же имени — обновляй его, второй файл не создавай. Если в файле уже другой модуль или класс — не смешивай: задай один вопрос и остановись. Каталог `.theory/` коммитится вместе с репозиторием.

В этом запуске меняется только файл в `.theory/`. Исходный код проекта не правь и рефакторинг не применяй. Код «до» и «после» лежит внутри этого markdown.

Язык файла — язык документации репозитория. Заголовки блоков оставь как в задании.

## Ход

1. Возьми модуль или класс из сообщения пользователя. Если его нет или названа система целиком — задай один вопрос и остановись до ответа. Если просят рефакторить без тестов, переписать всё за один заход или начать с самого сложного участка, у которого нет тестов, — откажись и остановись. Готово, когда названа одна единица и файл — её kebab-case.
2. Найди эту единицу в коде: длинный метод, завистливые функции, сквозные изменения, импорты и уже существующие тесты. Цикломатическую сложность бери из отчёта инструмента в репозитории. Отчёта нет — `> пробел:`, число не вычисляй сам. LOC и число зависимостей посчитай по этому файлу. Если в `.theory/bounded-context-mapping/`, `.theory/context-mapping/`, `.theory/ddd-bounded-contexts/` или `.theory/hexagonal-architecture/` уже есть это имя — прочитай их и сохрани его. Если есть `.theory/characterization-testing/` для этой единицы — прочитай и возьми уже зафиксированное поведение. Готово, когда каждый класс, метод и метрика взяты из репозитория либо помечены `> пробел:`. Модули, классы, метрики и справочные документы не выдумывай.
3. Если файл этой единицы в `.theory/refactoring-patterns/` уже есть — прочитай его и обнови, не создавая второй. Прочитай соседние файлы в том же каталоге и сохрани уже принятые имена. Готово, когда ясно, какой файл обновлять.
4. Закрой блоки задания ниже. Запах, которого нет в коде, не закрывай приёмом. Каталога приёмов в задании нет: бери устоявшееся имя (Extract Method, Introduce Parameter Object и подобные), только если оно ложится на найденный запах. Меньше трёх таких запахов — недостающие приёмы пометь `> пробел:`, не добирай список. Каждый приём — отдельный микро-шаг и отдельный PR, не один большой diff. «После (Факт)» оставь `> пробел:`: код в этом запуске не меняется. «После (План)» считай только там, где «До» измерено. Готово, когда каждый блок либо заполнен по источнику, либо помечен `> пробел:`.
5. Перед записью проверь антипаттерны. Первый микро-шаг — тесты на текущее поведение, если их ещё нет. Поведение в «после» то же, что в «до». Самый сложный непокрытый участок не стоит первым шагом. Готово, когда текст не расходится с разделом «Не делать».
6. Запиши файл в формате ниже. Готово, когда файл лежит по пути из первого раздела, а ответ пользователю называет этот путь и одну фразу: какой маленький шаг вместе с тестами упрощает структуру и оставляет поведение прежним.

## Формат файла

Один markdown-файл. Заголовок `#` — имя модуля или класса.

Разделы второго уровня, в этом порядке:

- «Метрики (До)» — таблица: цикломатическая сложность, LOC, число зависимостей. Рядом цель, запах и имя приёма. Цифры без источника — `> пробел:`;
- «Стратегия» — до трёх приёмов, каждый закрывает один видимый запах. Это цепочка отдельных PR, не один перепис;
- «Реализация» — на каждый приём: какое место он локализует, какие тесты страхуют поведение до правки, микро-шаги, контрастный код. «До» — фрагмент из репозитория в fenced-блоке. «После» — тот же фрагмент после одного приёма, во втором fenced-блоке. Новое имя метода появляется только как результат этого приёма. Нового модуля нет;
- «Метрики (После)» — та же таблица: план только по измеренному «До», факт — `> пробел:`;
- «Стратегия слияния» — один паттерн, один PR. Первым идёт покрытие текущего поведения, если тестов ещё нет.

Отдельный `refactoring_planning.md` не создавай. Исходники проекта не меняй. Дырка в знаниях — цитата `> пробел:`.

## Задание

Проанализируй <модуль или класс> с высокой когнитивной и цикломатической сложностью.

1. Метрики (До). Зафиксируй текущие cyclomatic complexity, lines of code (LOC) и количество зависимостей.
2. Стратегия. Выбери 3 наиболее эффективных приёма рефакторинга из каталога.
3. Реализация (для каждого приёма):
   - Обоснуй выбор: какую именно проблему локализует этот шаг.
   - Опиши тесты-страховки: что должно покрывать код перед изменением.
   - Дай пошаговый алгоритм применения (микро-шаги).
   - Покажи контрастный код: до и после (Before / After).
4. Метрики (После). Продемонстрируй расчет целевых метрик после применения всех 3 шагов.

## Шаги

1. Выявить запах кода. Найти проблемные места (длинный метод, завистливые функции, сквозные изменения) на основе анализа компонентов или архитектурных границ.
2. Обеспечить покрытие тестами. Запустить unit-тесты или тесты характеризации — перед началом рефакторинга все тесты должны быть «зелёными».
3. Выбрать один паттерн. Найти минимальный шаг для устранения конкретного «запаха» (например, сначала выделение метода, и только затем — выделение класса).
4. Применить и проверить. Выполнить шаг рефакторинга, убедиться, что тесты остаются «зелёными», а метрики сложности снизились.
5. Повторить. Выстроить цепочку из мелких изменений, фиксируя (commit) каждое успешное состояние кода.

## Не делать

- Рефакторинг без тестов: «тесты напишем потом» — прямой путь к регрессионным ошибкам.
- Большой взрыв под видом рефакторинга: переписать всё разом, так что незаметно меняется поведение. Это не рефакторинг.
- Попытка починить самый сложный участок сразу: начинать с изолированного, покрытого тестами места, чтобы сначала накопить уверенность и обкатать шаги.
