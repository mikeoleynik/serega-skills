# Architecture Decision Mapping

Построй хронологическую карту архитектурных решений одной системы и запиши её в репозиторий. Слот промпта — название системы. Файл один: `index.md`. Карта только из принятых решений не подходит: отклонённые тоже часть истории.

## Куда писать

`.theory/architecture-decision-mapping/index.md`

Слот — система целиком, отдельной сущности нет, поэтому имя файла всегда `index.md`. Название системы — в заголовке. Каталог создавай вместе с первым файлом. Повторный запуск обновляет этот файл, второй не создаёт. Если в файле уже записана другая система — не смешивай: задай один вопрос и остановись. Каталог `.theory/` коммитится вместе с репозиторием.

Язык файла — язык документации репозитория. Заголовки блоков оставь как в задании.

## Ход

1. Возьми название системы из сообщения пользователя. Если его нет — задай один вопрос и остановись до ответа. Готово, когда система названа и файл — `index.md`.
2. Собери решения из кода, документации и из `.theory/adr/`, если каталог есть. Для каждого нужен источник: ADR, коммит или документ. Готово, когда каждое решение, слой и метрика названы именем из репозитория либо помечены `> пробел:`.
3. Если `index.md` уже есть — прочитай его и обнови. Прочитай соседние файлы в `.theory/architecture-decision-mapping/` и сохрани уже принятые имена и номера решений. Готово, когда ясно, что обновляется один файл.
4. Закрой блоки задания ниже в хронологическом порядке. Дату бери из ADR, коммита или документа. Решение без даты пометь `> пробел:` и не вставляй его в середину цепочки по догадке. Слепую зону обозначай явно; компромисс или техдолг, которого репозиторий не подтверждает, пометь `> пробел:` и задай один вопрос. Готово, когда каждый пункт карточки либо подтверждён, либо помечен `> пробел:`.
5. Перед записью проверь антипаттерны. У решения есть триггер и явная связь с другими, не только дата. Отклонённые предложения включены, либо на их месте `> пробел:`. Новое решение дописывается в тот же `index.md`. Готово, когда карта не расходится с разделом «Не делать».
6. Запиши файл в формате ниже. Готово, когда файл лежит по пути из первого раздела, а ответ пользователю называет этот путь и одну фразу: текущее состояние — конечная точка, карта показывает пройденный путь и причины компромиссов.

## Формат файла

Один markdown-файл:

- заголовок `#` с названием системы;
- «Хронологическая цепочка» — одна линия: дата или спринт, решение, состояние системы после него, следующее решение. Замена записана явно, какое решение какое заменяет, а не просто стоит рядом по дате;
- «Детализация и связи» — карточка на каждое решение, в том же порядке. В карточке пункты задания: название и суть, триггер, результат (включая затронутые слои), метрики эволюционной архитектуры (fitness functions), статус. Статус — актуально, заменено (каким решением) или отклонено;
- «Пробелы и слепые зоны» — период без записей: что в системе видно по коду и какие последствия подтверждены. Неподтверждённый техдолг — цитата `> пробел:`.

Отдельный файл схемы не заводи.

## Задание

Сделай карту архитектурных решений (Architecture Decision Mapping) для системы: <система>.

Выведи все архитектурные решения (ADR) в строгом хронологическом порядке. Для каждого решения заполни пункты:

1. Название и суть решения.
2. Триггер — какая конкретно проблема, бизнес-требование или техническое ограничение заставили принять это решение.
3. Результат — что именно изменилось в архитектуре, кодовой базе или процессах после внедрения.
4. Метрики эволюционной архитектуры (Fitness Functions) — какие ключевые метрики или защитные функции системы улучшились или ухудшились в результате этого шага (например, поддерживаемость, отказоустойчивость, время отклика).
5. Статус — актуально или заменено (если заменено, укажи, каким именно решением).

Важное требование: восстанови «пропущенные звенья». Если между крупными изменениями системы были периоды без зафиксированных решений, явно выдели эти «слепые зоны» и предположи, какие неявные компромиссы или накопленный техдолг в это время возникли.

## Шаги

1. Соберите хронологию решений. Отсортируйте архитектурные решения (ADR) по дате. Отметьте их текущий статус: принято, заменено или устарело.
2. Привяжите к изменениям в системе. Для каждого решения укажите конкретный результат: разделение сервиса, смена технологии или внедрение нового шаблона.
3. Постройте цепочку замен. Свяжите решения явно: «Решение №3 заменяет Решение №1».
4. Найдите пробелы в эволюции. Выделите крупные рефакторинги, для которых не осталось записей. Это главные кандидаты на восстановление истории задним числом.
5. Свяжите с архитектурными слоями. Определите, какие уровни или контексты системы (данные, интеграция, бизнес-логика) затронуло каждое решение.

## Не делать

- Хронология без причинно-следственных связей: порядок по датам не означает, что событие А привело к событию Б. У каждого решения указывайте триггер и связь с другими.
- Карта только из принятых решений: отклонённые предложения тоже часть истории. Они показывают, какие пути рассматривались и почему от них отказались.
- Статичная карта: обновляйте файл при каждом новом архитектурном решении, а не оставляйте разовым документом.
