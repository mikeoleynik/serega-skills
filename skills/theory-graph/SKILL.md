# Theory Graph

Собери граф архитектурных знаний одного проекта или одного сервиса и запиши его в репозиторий. Слот промпта — название проекта или сервиса. Граф из абстрактных понятий без файлов, связи без типа и схема, которая остаётся только в голове техлида, не подходят.

## Куда писать

`.theory/theory-graph/<субъект>.md`

Слот — одно имя, проект или сервис.

Назван один сервис — имя файла kebab-case этого сервиса: нижний регистр, слова через дефис, латиница (`Сервис уведомлений` → `servis-uvedomleniy.md`). Назван проект или система целиком и отдельного сервиса нет — файл `index.md`, название в заголовке. Краткое описание, если оно есть в сообщении или в документах репозитория, — первая строка под заголовком, не отдельный файл. Каталог создавай вместе с первым файлом. Повторный запуск для того же проекта или того же сервиса обновляет этот файл, второй не создаёт. Если в `index.md` уже другой проект — не смешивай: задай один вопрос и остановись. Если в файле сервиса уже другой сервис — не смешивай: задай один вопрос и остановись. Каталог `.theory/` коммитится вместе с репозиторием.

Узлы, термины глоссария и предложенные документы живут в этом одном markdown. Отдельные `GLOSSARY.md`, `docs/adr/` и базу графа не создавай.

Язык файла — язык документации репозитория. Заголовки блоков оставь как в задании.

## Ход

1. Возьми название проекта или сервиса из сообщения пользователя. Если его нет — задай один вопрос и остановись до ответа. Если названы и проект целиком, и отдельный сервис и неясно, какой слот писать — задай один вопрос и остановись, два файла не пиши. Краткое описание вторым вопросом не спрашивай: есть в сообщении или в документах — поставь под заголовок, нет — `> пробел:`. Если просят граф абстрактных понятий без файлов, связи «просто связано» без типа или схему только в голове, в вики вне репозитория или в базе графа — откажись и остановись. Готово, когда назван один проект (файл — `index.md`) или один сервис (файл — kebab-case его имени).
2. Собери узлы из реальных файлов репозитория и из уже лежащих каталогов `.theory/`: ADR, диаграммы, термины глоссария, карты процессов, эталонная архитектура. Документа нет — это пробел, не узел. Если уже есть `.theory/adr/`, `.theory/architecture-decision-mapping/`, `.theory/bounded-context-mapping/`, `.theory/context-mapping/`, `.theory/conway-mapping/`, `.theory/system-theory-anchor/` или другие каталоги `.theory/` — прочитай их и бери узлами эти файлы, имена внутри не подменяй. Номер ADR бери из файла. Нового номера не придумывай. Готово, когда каждый узел — путь к файлу из репозитория либо помечен `> пробел:`. Команды, глоссарные термины и ADR не выдумывай.
3. Если файл этого субъекта в `.theory/theory-graph/` уже есть — прочитай его и обнови, не создавая второй. Прочитай соседние файлы в том же каталоге и сохрани уже принятые имена узлов. В `index.md` уже другой проект — не смешивай: задай один вопрос и остановись. Готово, когда ясно, какой файл обновлять.
4. Закрой блоки задания ниже. Ребро ставь только между двумя существующими узлами и только одним из четырёх типов. Типа по текстам не видно — ребро не рисуй, пометь `> пробел:`. «Противоречит» и «заменяет» — только если расхождение или смена решения написаны в самих файлах. Слепую зону записывай на компонент или сценарий, который есть в коде и ни один документ его не покрывает. Устаревший узел — документ, чьё утверждение расходится с кодом или с более новым файлом в репозитории. Срок «старше 6 месяцев», Mongo, ADR-002 и ADR-012 из примера не копируй. Список из 2–3 пробелов и топ-3 действий — потолок задания, не квота: неподтверждённые пункты не добирай. Документ из Action Items в граф узлом не добавляй и файлом не создавай. Готово, когда каждый блок либо заполнен по источнику, либо помечен `> пробел:`.
5. Перед записью проверь антипаттерны. У каждого узла есть путь к реальному файлу. У каждого ребра ровно один тип из четырёх: «основан на», «детализирует», «противоречит», «заменяет». Других типов нет. Граф записан в файл репозитория. Подтверждённых узлов нет совсем — задай один вопрос и остановись, файл из пустого графа не пиши. Готово, когда текст не расходится с разделом «Не делать».
6. Запиши файл в формате ниже. Готово, когда файл лежит по пути из первого раздела, а ответ пользователю называет этот путь и одну фразу: какой документ фиксирует, почему код устроен так, и какая часть системы всё ещё без этой записи.

## Формат файла

Один markdown-файл:

- заголовок `#` с названием проекта или сервиса. Краткое описание — следующая строка, если оно есть в источнике;
- «Граф» — список связей. Строка: имя узла, тип связи, имя узла. Тип только один из четырёх. У узла в скобках путь к файлу. Под списком один fenced-блок `mermaid` с `graph TD`: те же узлы и те же рёбра, подпись стрелки — тип связи. Изолированный узел, у которого нет рёбер, остаётся в списке узлов над рёбрами;
- «Пробелы» — markdown-таблица. Колонки: категория, статус или проблема, описание, критичность, действие. Категория — слепая зона или устаревший узел. Одна строка — одна дыра, подтверждённая репозиторием;
- «Action Items» — до трёх документов, которых ещё нет и которые закрывают строки таблицы. Это список в том же файле. Номера будущих ADR здесь нет.

Отдельные `arch-template.md` и `matrix-teams-services.md` не создавай. Дырка в знаниях — цитата `> пробел:`.

## Задание

Построй Theory Graph (граф архитектурных знаний) для проекта или сервиса: <проект или сервис>.

Изучи артефакты репозитория и уже лежащие файлы `.theory/` и сформируй граф по следующим правилам:

1. Спецификация узлов:
Каждым узлом должен быть конкретный документ или сущность: ADR (с номерами), диаграммы (C4, Context, Flow), термины глоссария, статьи из reference architecture.

2. Спецификация рёбер (типы связей):
Строго используй только следующие направленные связи:
— «основан на» (зависимость от концепта/документа)
— «детализирует» (декомпозиция или шаг углубления)
— «противоречит» (конфликт решений или устаревшие данные)
— «заменяет» (актуализация старых ADR/схем)

3. Анализ слепых зон (Theory Gaps):
Выяви «изолированные» узлы и критические части системы, которые не покрыты связями или документацией (где теория системы утеряна или не зафиксирована).

Формат вывода:
1. Граф: Список связей в формате [Узел А] —(тип связи)—> [Узел Б].
2. Пробелы: Список из 2-3 критических слепых зон.
3. Action Items: Топ-3 конкретных узла (документа), которые команде нужно создать в первую очередь для закрытия этих пробелов.

Исходные данные для анализа — файлы репозитория и каталоги `.theory/`. Отдельный текст от пользователя не жди.

## Шаги

1. Соберите артефакты. Соберите всё, что уже создано — ADR, диаграммы, глоссарий, инструкции.
2. Типизируйте узлы. Разделите документы по типам: решение, диаграмма, термин глоссария, карта процессов, базовая архитектура.
3. Свяжите рёбрами. ADR-005 «детализирует» C4; глоссарий «основан на» Event Storming.
4. Найдите слепые зоны. Выявите компоненты системы, к которым не привязан ни один документ.
5. Найдите устаревшие узлы. Выделите артефакты, которые не обновлялись после крупных релизов или изменения архитектуры.

## Не делать

- Граф ради графа: каждый узел ссылается на реальный файл, а не на абстрактную концепцию.
- Без типов связей: только «основан на», «детализирует», «противоречит», «заменяет». Связи без типа нет.
- Граф в голове техлида: карта связей лежит в репозитории и доступна команде. База графа и файл вне `.theory/theory-graph/` этот запуск не создаёт.
