# Contract Testing

Спроектируй контрактное тестирование одной интеграции consumer и provider и запиши контракт в репозиторий. Слоты промпта — имя consumer-сервиса и имя provider-сервиса. Стек бери из репозитория. Контракт вместо сквозной бизнес-логики, проверка, которую запрещено автоматизировать, и одна схема на все точки интеграции пары не подходят.

## Куда писать

`.theory/contract-testing/<consumer>-<provider>.md`

Один файл на пару. Оба имени — kebab-case, латиница, между ними дефис (`BillingService` и `UserService` → `billing-service-user-service.md`, `Сервис заказов` и `Биллинг` → `servis-zakazov-billing.md`). Каталог создавай вместе с первым файлом. Повторный запуск для той же пары обновляет этот файл. Сначала прочитай каталог: если запись пары уже лежит под другим разбиением дефисов — обновляй её, второй файл не создавай. Каталог `.theory/` коммитится вместе с репозиторием.

Файл — запись контракта, не новый тест в тестовом наборе проекта. Схема, примеры payload и шаблоны тестов лежат внутри этого markdown, в fenced-блоках. В каталог тестов и в CI репозитория ничего не добавляй.

Язык файла — язык документации репозитория. Заголовки блоков оставь как в задании.

## Ход

1. Возьми оба имени из сообщения пользователя. Если не хватает одного или обоих — задай один вопрос и остановись до ответа. Стек в этом шаге не спрашивай: его закроет шаг 2. Если контрактами просят заменить сквозные тесты бизнес-логики, оставить контракт без проверки в CI или слить все точки интеграции пары в одну схему — откажись и остановись. Готово, когда названы consumer и provider.
2. Найди в коде реальные вызовы этой пары: эндпоинты, события, поля, статусы и стек тестов. Точку для первого контракта возьми ту, которую назвал пользователь. Если не назвал — самую хрупкую из тех, что видны в коде между этими двумя сервисами. Если таких несколько и неясно, какую брать первой, пометь `> пробел:` и задай один вопрос, не выбирай за пользователя. Чужие пары в этот файл не пиши. Готово, когда каждое имя сервиса, поле, статус и точка интеграции взяты из репозитория либо помечены `> пробел:`. Модули, сервисы, команды и контракты не выдумывай.
3. Если файл этой пары в `.theory/contract-testing/` уже есть — прочитай его и обнови, не создавая второй. Прочитай соседние записи в том же каталоге и сохрани уже принятые имена точек. Готово, когда ясно, какой файл обновлять.
4. Закрой блоки задания ниже для выбранной точки. Поле, статус, схема или пример payload, которых нет в коде, пометь `> пробел:` и задай один вопрос. Успешный сценарий и ошибочные ответы бери из кода: нет примера ошибки — `> пробел:`, код ошибки не выдумывай. Другие реальные точки этой же пары перечисли в реестре отдельными строками, без общей схемы. Точки, которой нет в коде, в реестр не добавляй и до пяти не добирай. Шаблон теста пиши на языке репозитория. Языка в репозитории не видно — пометь `> пробел:`, пример Pact на Go, Java или TypeScript не подставляй. Проверку поставщика и правила эволюции контракта опиши по тому, что уже есть в репозитории. Workflow или правил версий нет — `> пробел:`, файл пайплайна не создавай. Готово, когда каждый блок либо заполнен по источнику, либо помечен `> пробел:`.
5. Перед записью проверь антипаттерны. Контракт проверяет границу и формат, не сквозной сценарий. У выбранной точки есть способ верификации поставщика, либо явный `> пробел:` вместо обещания, что CI уже это делает. У каждой точки своя схема, не один контракт на все эндпоинты пары. Изоляция — отдельные схемы внутри этой записи пары, не второй markdown. Готово, когда текст не расходится с разделом «Не делать».
6. Запиши файл в формате ниже. Готово, когда файл лежит по пути из первого раздела, а ответ пользователю называет этот путь и одну фразу: какая договорённость consumer и provider стала явной проверкой и какое ломающее изменение поставщика она ловит до продакшена.

## Формат файла

Один markdown-файл. Заголовок `#` — оба имени.

Разделы второго уровня, в этом порядке:

- «Точка интеграции» — какая точка выбрана первой и почему она самая хрупкая. В промпте у этого шага нет короткого заголовка, бери эти слова;
- «Формат и схема контракта» — REST/OpenAPI, JSON Schema, gRPC proto или AsyncAPI, по тому, что есть в коде. Схема — fenced-блок `json` или `yaml`;
- «Consumer-driven подход» — два подраздела: «Ожидания Consumer» (критичные поля и статусы, какие моки из них следуют) и «Верификация Provider» (как гонять проверку на реальном коде поставщика). В конце верификации одна фраза, как проверка запускается в CI, и правила эволюции контракта, если они есть в репозитории. Пайплайна или правил нет — цитата `> пробел:`;
- «Спецификация контракта» — пример спецификации fenced-блоком, в коде или JSON/YAML, полями из репозитория. Рядом примеры payload запроса и ответа своими fenced-блоками, включая ошибочные ответы, которые есть в коде;
- «Шаблон теста Consumer» и «Шаблон теста Provider» — по fenced-блоку на языке репозитория;
- «Реестр точек интеграции» — markdown-таблица. Колонки: вызывающий сервис (Consumer), поставщик (Provider), точка интеграции (эндпоинт или событие), тип контракта, статус покрытия. Каждая точка этой пары — отдельная строка. Полная спецификация в этом файле — у выбранной первой точки.

Файл остаётся в `.theory/`. Отдельные `contract.json`, `github-actions-demo.yml`, `registry.md` и файлы в тестовом каталоге проекта не создавай. Дырка в знаниях — цитата `> пробел:`.

## Задание

Спроектируй Contract Testing для интеграции <consumer-сервис> ↔ <provider-сервис>.

Выполни задачу по шагам:

1. Выбери самую хрупкую и критичную точку интеграции (integration point) между ними для первого контракта и обоснуй выбор.
2. Определи формат и схему контракта (REST/OpenAPI, JSON Schema, gRPC proto или AsyncAPI для event-driven).
3. Опиши Consumer-driven подход:
   - Сформулируй ожидания (expectations) на стороне Consumer (какие поля/статусы критичны, какие моки генерировать).
   - Опиши схему верификации на стороне Provider (как запускать тесты на реальном коде поставщика).
4. Напиши пример спецификации контракта (в коде или JSON/YAML) и шаблон теста для Consumer и Provider на <стек>.

Результат должен быть готов к переносу в репозиторий.

## Шаги

1. Найти критичные точки интеграции. Выбрать топ-5 самых хрупких связей на основе карты зависимостей (Dependency Mapping) и анализа трафика (Runtime Flow).
2. Выбрать формат. Определить инструмент — Pact (подход consumer-driven), сравнение схем OpenAPI (OpenAPI diff) или реестр схем (Schema Registry) для событийной архитектуры.
3. Написать первый контракт. Покрыть минимальный успешный сценарий (happy path) и 1–2 основных кейса с ошибками.
4. Настроить проверку на стороне поставщика в CI. Автоматизировать верификацию (Provider verification), чтобы сборка поставщика сервиса падала при нарушении контракта.
5. Внедрить стратегию версионирования. Определить правила эволюции контрактов, чтобы изменения на бэкенде не ломали текущих потребителей.

## Не делать

- Использовать контрактные тесты вместо сквозных (E2E): контракты защищают только границы сервисов и форматы данных, но не тестируют сквозную бизнес-логику системы.
- Проверки без автоматизации в CI: если файлы контрактов лежат в репозитории, но не проверяются при каждом пуле — это мертвая документация, которая быстро устареет.
- Один гигантский контракт на всё: попытка описать всё взаимодействие сервисов в одном файле приводит к путанице. Для каждой точки интеграции (эндпоинта или события) должен быть отдельный изолированный контракт.
