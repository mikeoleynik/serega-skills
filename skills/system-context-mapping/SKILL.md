# System Context Mapping

Построй карту контекста одного сервиса и запиши её в репозиторий. Слот промпта — название сервиса. Сервис на схеме — один чёрный ящик. Внутренние модули, слои и чужая база как своя на этой карте не подходят.

## Куда писать

`.theory/system-context-mapping/<сервис>.md`

Имя файла — kebab-case сервиса: нижний регистр, слова через дефис, латиница (`Order Service` → `order-service.md`, `Сервис заказов` → `servis-zakazov.md`). Слот — один сервис, не проект целиком, поэтому файл не `index.md`. Каталог создавай вместе с первым файлом. Повторный запуск для того же сервиса обновляет этот файл. Сначала прочитай каталог: если карта уже лежит под другим написанием того же имени — обновляй её, второй файл не создавай. Если в файле уже другой сервис — не смешивай: задай один вопрос и остановись. Каталог `.theory/` коммитится вместе с репозиторием.

Язык файла — язык документации репозитория. Заголовки блоков оставь как в задании.

## Ход

1. Возьми название сервиса из сообщения пользователя. Если его нет — задай один вопрос и остановись до ответа. Названа только система целиком, а сервис не назван — тот же один вопрос, `index.md` не пиши. Если просят раскрыть внутренние модули, слои или базы внутри сервиса — откажись и остановись. Готово, когда назван один сервис и файл — его kebab-case.
2. Найди в коде акторов, внешние системы, входящие и исходящие потоки, протоколы и то, что сервис не делает. Очереди, планировщики и вебхуки ищи так же, как синхронные API. База, которую сервис только читает и которая принадлежит другому сервису, — внешняя зависимость. Если уже есть `.theory/c4-model/`, `.theory/architecture-decision-mapping/` или `.theory/evolutionary-architecture/` — прочитай их и сохрани эти имена акторов, систем и границ, где они про этот сервис. Готово, когда каждый актор, система, поток и протокол названы именем из репозитория либо помечены `> пробел:`. Модули, сервисы, брокеры и протоколы не выдумывай.
3. Если файл этого сервиса в `.theory/system-context-mapping/` уже есть — прочитай его и обнови, не создавая второй. Прочитай соседние файлы в том же каталоге и сохрани уже принятые имена. В файле уже другой сервис — не смешивай: задай один вопрос и остановись. Готово, когда ясно, какой файл обновлять.
4. Закрой блоки задания ниже. Назначение, актор, внешняя система, направление, протокол или пункт «вне контекста», которых нет в коде и в сообщении пользователя, пометь `> пробел:` и задай один вопрос. Имена из примера (Клиент, CoreService, платёжный шлюз, брокер, gRPC-очистка) не копируй. Готово, когда каждый блок либо заполнен по источнику, либо помечен `> пробел:`.
5. Перед записью проверь антипаттерны. В центре схемы один блок — этот сервис, без модулей и слоёв внутри. Асинхронная связь, которая есть в коде, есть и на карте. Чужая база не лежит внутри зоны ответственности. Готово, когда текст не расходится с разделом «Не делать».
6. Запиши файл в формате ниже. Готово, когда файл лежит по пути из первого раздела, а ответ пользователю называет этот путь и одну фразу: сервис зафиксирован как один узел, а внешние связи — как явные контракты границ ответственности.

## Формат файла

Один markdown-файл:

- заголовок `#` с именем сервиса;
- «Назначение и ценность» — одно предложение: какую главную бизнес-задачу решает сервис и зачем он существует;
- «Границы и окружение» — два списка: акторы (кто напрямую взаимодействует) и внешние системы (сторонние сервисы, базы, платформы);
- «Потоки данных и интеграции» — у каждой входящей и исходящей связи направление, назначение и протокол. В этом же файле один fenced-блок `mermaid` с `graph TD`: сервис — один узел в центре, акторы и внешние системы снаружи, подпись стрелки — протокол и назначение. Узлы — имена из репозитория;
- «Вне контекста (Out of Scope)» — что лежит за ответственностью этого сервиса и делегировано другим системам.

Отдельный `arch-template.md` не создавай. Дырка в знаниях — цитата `> пробел:`.

## Задание

Построй System Context Map для сервиса <сервис>, рассматривая его строго как «черный ящик».

Собери информацию и структурируй ответ по следующим блокам:

1. Назначение и ценность: Кратко сформулируй, какую главную бизнес-задачу решает сервис и зачем он существует.
2. Границы и окружение:
   - Акторы: Кто (пользователи, роли) напрямую взаимодействует с сервисом.
   - Внешние системы: С какими сторонними сервисами, базами данных или платформами он связан.
3. Потоки данных и интеграции: Для каждой входящей и исходящей связи укажи:
   - Направление потока данных.
   - Назначение (какую бизнес- или техническую функцию выполняет).
   - Протокол / Технологию взаимодействия (REST API, gRPC, WebSockets, Kafka и т.д.).
4. Вне контекста (Out of Scope): Что принципиально находится за границами ответственности этого сервиса и делегировано другим системам.

Выведи результат в виде структурированных списков, а связи (пункт 3) оформи в виде понятной текстовой схемы (например, Mermaid.js) или таблицы. Не погружайся во внутреннюю архитектуру и код сервиса.

## Шаги

1. Определить целевой сервис. Разместить один блок в центре схемы. Сформулировать одним предложением: «Этот сервис отвечает за...».
2. Выявить акторов. Определить, кто или что инициирует взаимодействие — пользователи, смежные сервисы, планировщики (cron) или очереди задач.
3. Определить внешние системы. Выписать всё, что находится за рамками вашего кода, но связано с ним — базы данных, сторонние API, брокеры сообщений, легаси-системы.
4. Прописать связи. Для каждого входящего и исходящего потока указать направление, передаваемые данные и цель взаимодействия (не просто «REST», а «REST: передача логов»).
5. Проверить границы. Четко разделить зоны. Всё, что внутри центрального блока — зона ответственности вашей команды; всё, что вынесено наружу — внешние зависимости.

## Не делать

- Проектировать внутреннюю структуру: детализация модулей, баз данных или слоёв внутри сервиса на этом этапе — ошибка. Сервис остаётся строго одним блоком. Для деталей есть уровень контейнеров C4.
- Игнорировать асинхронные интеграции: пропуск очередей сообщений, планировщиков и вебхуков. Асинхронные связи — такие же границы системы, как синхронные API.
- Путать владение данными и зависимость: база данных другого сервиса — не своя. Если сервис только читает чужие данные, это внешняя зависимость, а не владение.
