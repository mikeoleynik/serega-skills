# Runtime Flow Mapping

Построй карту выполнения одного асинхронного сценария и запиши её в репозиторий. Слот промпта — название сценария. Вся система, несколько сценариев на одной схеме, маршрут по документации без кода и пропуск очередей с воркерами не подходят.

## Куда писать

`.theory/runtime-flow-mapping/<сценарий>.md`

Один файл на сценарий. Имя файла — kebab-case сценария: нижний регистр, слова через дефис, латиница (`Оплата заказа и запуск доставки` → `oplata-zakaza-i-zapusk-dostavki.md`). Слот — один сценарий, не система, поэтому файл не `index.md`. Каталог создавай вместе с первым файлом. Повторный запуск для того же сценария обновляет этот файл. Сначала прочитай каталог: если карта уже лежит под другим написанием того же имени — обновляй её, второй файл не создавай. Если в файле уже другой сценарий — не смешивай: задай один вопрос и остановись. Каталог `.theory/` коммитится вместе с репозиторием.

Язык файла — язык документации репозитория. Заголовки блоков оставь как в задании.

## Ход

1. Возьми сценарий из сообщения пользователя. Если его нет — задай один вопрос и остановись до ответа. Если названа система целиком или несколько сценариев — задай один вопрос, какой сценарий писать, и остановись, два файла не пиши. Если просят собрать схему по документации, памяти или старому ТЗ без кода, смешать независимые процессы на одной схеме или оборвать путь фразой «дальше обработает воркер» — откажись и остановись. Готово, когда назван один сценарий и файл — его kebab-case.
2. Найди этот сценарий в коде: входную точку, отправителя, получателя, транспорт, запись в хранилище и побочный эффект каждого шага. Триггер — тот, что есть в коде: HTTP-запрос, сообщение из брокера, cron или вебхук. Очередь, брокер и фоновый обработчик, которые есть на пути, — отдельные шаги. Если уже есть `.theory/bounded-context-mapping/`, `.theory/context-mapping/`, `.theory/conway-mapping/` или `.theory/runtime-flow-mapping/` — прочитай их и сохрани эти имена сервисов и потоков. Готово, когда каждый участник, топик, эндпоинт и поток названы именем из репозитория либо помечены `> пробел:`. Модули, владельцев, эндпоинты и потоки не выдумывай.
3. Если файл этого сценария в `.theory/runtime-flow-mapping/` уже есть — прочитай его и обнови, не создавая второй. Прочитай соседние файлы в том же каталоге и сохрани уже принятые имена. Готово, когда ясно, какой файл обновлять.
4. Закрой блоки задания ниже. Шаг, транспорт, смена состояния, гонка, retry, DLQ или место идемпотентности, которых нет в коде, пометь `> пробел:` и задай один вопрос. Имена из примера (Клиент, API Gateway, Order Service, Kafka, `order.created`, `POST /orders`) не копируй. Политику повторов не назначай числом, которого нет в коде. Готово, когда каждый блок либо заполнен по источнику, либо помечен `> пробел:`.
5. Перед записью проверь антипаттерны. Маршрут собран по коду, не по старой схеме. На схеме один сценарий. Асинхронный шаг, который есть в коде, записан как полный переход: отправитель, транспорт, получатель. Такого шага нет в коде — `> пробел:`, брокер не подставляй. Гонку записывай, только если она видна в коде; не видна — `> пробел:`, не объявляй поток безопасным. Готово, когда текст не расходится с разделом «Не делать».
6. Запиши файл в формате ниже. Готово, когда файл лежит по пути из первого раздела, а ответ пользователю называет этот путь и одну фразу: какой триггер запускает сценарий и на каком шаге поток блокируется, ветвится или ждёт повтор.

## Формат файла

Один markdown-файл. Заголовок `#` — название сценария.

Разделы второго уровня, в этом порядке:

- «Шаги» — путь от триггера до стабильного состояния, по одному шагу (hop). У каждого шага три пункта задания: «Отправитель и Получатель», «Транспорт» (топик или очередь, брокер, Pub/Sub или Point-to-Point), «Изменение состояния» (какая сущность меняется и какие побочные эффекты). Это текстовая схема последовательности с коротким техническим комментарием к шагу;
- «Узкие места и точки отказа» — три списка: где возможны гонка или нарушение порядка сообщений; как код ведёт себя при сбое подписчика (retry, DLQ); где обработка должна быть идемпотентной. Механизма в коде нет — `> пробел:` у этого пункта.

В конце один fenced-блок `mermaid` с `sequenceDiagram` в этом же файле. Участники и сообщения — имена из репозитория. Автонумерация совпадает с порядком шагов. Асинхронный переход — сообщение к участнику очереди или воркера, не примечание «дальше воркер». Точку отказа, которая видна в коде, пометь заметкой на этом сообщении. Отдельный `standard-diagram.md` не создавай. Дырка в знаниях — цитата `> пробел:`.

## Задание

Построй Runtime Flow Map для асинхронного сценария: <сценарий>.

Проследи путь от начального триггера до перехода системы в финальное стабильное состояние. Для каждого шага (hop) укажи:

1. Отправитель и Получатель: Сервис/модуль, генерирующий событие, и подписчики.
2. Транспорт: Название топика/очереди, брокер (Kafka, RabbitMQ и т.д.) и тип взаимодействия (Pub/Sub, Point-to-Point).
3. Изменение состояния: Какая бизнес-сущность меняется и какие побочные эффекты (side effects) возникают.

Особое внимание удели узким местам и точкам отказа:

- Где возможны гонки данных (race conditions) или нарушение порядка сообщений.
- Как система поведет себя при сбое подписчика (retry policy, DLQ).
- В каких точках критически важна идемпотентность обработки.

Формат вывода: Текстовая схема последовательности (последовательные шаги) с краткими техническими комментариями к каждому шагу.

## Шаги

1. Выберите один сценарий. Успешный путь (happy path) одного пользовательского сценария или доменного события — не пытайтесь описать всю систему сразу.
2. Найдите триггер. Входная точка процесса — HTTP-запрос, сообщение из брокера, запуск по расписанию (cron) или вебхук.
3. Проследите пошагово каждый переход. Каждый межсервисный вызов, отправка события в шину или запись в базу данных — это отдельный шаг (hop).
4. Отметьте изменения состояния. Зафиксируйте, в каких точках данные создаются, обновляются или удаляются в базах данных.
5. Добавьте сценарии сбоев. Опишите поведение системы при таймаутах, повторных попытках (retries) и отправке сообщений в очередь ошибок (DLQ) — как минимум для критически важных шагов.

## Не делать

- Карта из документации, а не из кода: проектирование схемы «по памяти» или по старым ТЗ приводит к ошибкам. Маршрут нужно проверять по коду или на тестовом стенде через сквозное логирование (trace/log correlation).
- Смешивание сценариев: попытка уместить несколько независимых процессов на одной схеме превращает её в кашу. Один сценарий — одна диаграмма.
- Игнорирование асинхронности: подход в духе «там дальше обработает воркер» маскирует реальную картину. Асинхронная очередь и фоновый обработчик — это полноценные шаги системы, а не просто пунктирная стрелка.
