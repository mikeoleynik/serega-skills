# Hexagonal Architecture

Разложи один сервис или модуль на ядро, порты и адаптеры и запиши схему в репозиторий. Слот промпта — название сервиса или модуля. Порт на каждый CRUD-метод, пустое ядро как целевая схема и один адаптер на всё не подходят.

## Куда писать

`.theory/hexagonal-architecture/<сервис-или-модуль>.md`

Имя файла — kebab-case сервиса или модуля: нижний регистр, слова через дефис, латиница (`OrderService` → `order-service.md`). Слот — одна единица, не проект целиком, поэтому файл не `index.md`. Каталог создавай вместе с первым файлом. Повторный запуск для той же единицы обновляет этот файл. Сначала прочитай каталог: если схема уже лежит под другим написанием того же имени — обновляй её, второй файл не создавай. Если в файле уже другой сервис или модуль — не смешивай: задай один вопрос и остановись. Каталог `.theory/` коммитится вместе с репозиторием.

В этом запуске меняется только файл в `.theory/`. Папки и классы в коде не создавай.

Язык файла — язык документации репозитория. Заголовки блоков оставь как в задании.

## Ход

1. Возьми название сервиса или модуля из сообщения пользователя. Если его нет или названа система целиком — задай один вопрос и остановись до ответа. Если просят завести порт на каждый CRUD-метод, оставить ядро пустым как целевую схему или собрать один адаптер на все выходы — откажись и остановись. Готово, когда названа одна единица и файл — её kebab-case.
2. Найди эту единицу в коде: сущности, объекты-значения, сценарии, входящие адаптеры (HTTP, CLI, потребители очередей), исходящие порты и их реализации, импорты ядра. Если модуля в репозитории нет — задай один вопрос и остановись, каталог и порты не выдумывай. Если в `.theory/bounded-context-mapping/`, `.theory/context-mapping/` или `.theory/event-driven-architecture/` уже есть контексты, карта или события — прочитай их и сохрани эти имена. Готово, когда каждый порт, адаптер и модуль назван именем из репозитория либо помечен `> пробел:`. Модули, события, команды людей и фитнес-функции не выдумывай.
3. Если файл этой единицы в `.theory/hexagonal-architecture/` уже есть — прочитай его и обнови, не создавая второй. Прочитай соседние файлы в том же каталоге и сохрани уже принятые имена. Готово, когда ясно, какой файл обновлять.
4. Закрой блоки задания ниже. Правило, сценарий, порт или адаптер, которых нет в коде, пометь `> пробел:` и задай один вопрос. Имена из примера (CreateOrderUseCase, REST, GraphQL, Postgres, Kafka, Spring) не копируй. Целевое дерево каталогов, которого нет в репозитории, — `> пробел:`. Готово, когда каждый блок либо заполнен по источнику, либо помечен `> пробел:`.
5. Перед записью проверь антипаттерны. Порт отвечает сценарию, который есть в ядре, и не повторяет метод репозитория. Поведение, которое лежит в сервисах при пустых сущностях, запиши в критическом анализе как разрыв. Адаптер на несколько независимых выходов тоже запиши туда. Границу, которая уже есть в коде, назови. Новой нарезки нет в репозитории — `> пробел:`. Целевое направление зависимостей — к ядру. Фактический импорт ядра наружу оставь на схеме как есть и повтори в критическом анализе. Готово, когда текст не расходится с разделом «Не делать».
6. Запиши файл в формате ниже. Готово, когда файл лежит по пути из первого раздела, а ответ пользователю называет этот путь и одну фразу: какой порт держит контракт ядра и какой адаптер заменяется без правки бизнес-правил.

## Формат файла

Один markdown-файл:

- заголовок `#` с именем сервиса или модуля;
- три раздела второго уровня, в этом порядке: «Domain Core», «Inbound Ports & Adapters (Вход)», «Outbound Ports & Adapters (Выход)»;
- в «Domain Core» — сущности, объекты-значения и сценарии, которые есть в коде, и правила, которые они держат;
- во «Входе» — порты сценариев и адаптеры, которые их вызывают: контроллеры, CLI, потребители очередей;
- в «Выходе» — порты, которые нужны ядру, и реализации, которые есть в коде: репозитории, клиенты внешних API, издатели сообщений;
- «Критический анализ» — места, где ядро импортирует аннотацию фреймворка, ORM-сущность или инфраструктурную библиотеку. Рядом путь файла. Таких импортов нет — так и напиши;
- «Схема связей» — один fenced-блок `mermaid` с `graph TD` в этом же файле. Узлы — имена из репозитория. Снаружи инфраструктура, внутри ядро. Стрелка показывает фактический вызов или реализацию порта;
- «Структура каталогов» — дерево фактических путей модуля в одном fenced-блоке. Каталога в репозитории нет — `> пробел:`.

Отдельный `sequence-diagram.md` не создавай. Дырка в знаниях — цитата `> пробел:`.

## Задание

Спроектируй или проанализируй <сервис или модуль>, строго следуя принципам Hexagonal Architecture.

Раздели решение на три слоя и опиши их состав:

1. Domain Core: Чистая бизнес-логика (Entities, Value Objects, Use Cases/Services). Напиши, какие основные правила и сценарии здесь живут.
2. Inbound Ports & Adapters (Вход): Как мир управляет приложением. Выдели порты (интерфейсы сценариев) и адаптеры (REST-контроллеры, CLI, consumer-ы очередей).
3. Outbound Ports & Adapters (Выход): Как приложение управляет миром. Выдели порты (интерфейсы SPI для БД, внешних API) и их конкретные реализации (Postgres-репозитории, Kafka-паблишеры).

Критический анализ:
Явно подсвети нарушения границ архитектуры (Anti-Patterns): места, где Domain Core напрямую импортирует аннотации фреймворка (например, Spring, ORM-сущности) или зависит от инфраструктурных библиотек.

Выдай результат в виде краткой текстовой схемы связей и структуры каталогов (папок) для этого модуля.

## Шаги

1. Выделите ядро (Domain Core). Сформулируйте бизнес-сценарии (Use Cases) и сущности (Entities). Главное правило: ноль импортов сторонних фреймворков, ORM или HTTP-библиотек.
2. Определите входные порты (Inbound Ports). Создайте интерфейсы, через которые внешний мир будет управлять ядром (например, CreateOrderUseCase).
3. Определите выходные порты (Outbound Ports). Создайте интерфейсы для сервисов, которые нужны самому ядру для работы с внешним миром (например, OrderRepository, PaymentGateway).
4. Реализуйте адаптеры (Adapters). Напишите конкретный инфраструктурный код — контроллеры, репозитории, обработчики очередей, — который реализует или вызывает ваши порты.
5. Проверьте направление зависимостей. Убедитесь, что все стрелки зависимостей направлены строго внутрь. Инфраструктура зависит от бизнес-логики, но не наоборот.

## Не делать

- Порты под каждый CRUD-метод: Не каждый метод репозитория должен быть отдельным портом. Порты создаются под конкретные потребности бизнес-логики, а не просто дублируют функции базы данных.
- Анемичный гексагон: Доменное ядро остается пустым, а вся реальная логика оседает в «прикладных сервисах». Архитектура превращается в форму без содержания.
- Адаптер-божественный класс: Один гигантский адаптер на тысячи строк кода, который делает всё сразу. Разделяйте адаптеры по логическому смыслу и контекстам.
